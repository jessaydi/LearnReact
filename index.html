Qu'est-ce que le DOM ?

Quand tu ouvres une page web, voici ce qui se passe, dans l'ordre :

  1. Le serveur envoie un fichier HTML. Ce n'est que du texte.
  2. Le navigateur lit ce texte et construit en mémoire un arbre d'objets : un objet par balise, rangé dans son parent. Cet arbre s'appelle le DOM (Document Object Model, « le modèle objet du document »).
  3. Le navigateur dessine l'écran à partir de cet arbre. Pas à partir du texte HTML : à partir du DOM.
  4. JavaScript peut lire et modifier cet arbre. Dès qu'un objet change, le navigateur redessine la partie de l'écran concernée.

Le cycle complet : données, React, DOM, écran

Voici le schéma à garder en tête pour tout le cours. Chaque étape a un responsable : toi, React, le navigateur ou l'utilisateur.

  1. toiLes donnéesla liste des tâches, rangée dans l'état du composant
  2. ton codeTes composants décrivent l'écranReact appelle tes fonctions ; elles renvoient l'écran voulu pour ces données
  3. ReactReact comparenouvelle description contre ancienne : où sont les différences ?
  4. ReactReact modifie le DOMseulement là où il y a une différence
  5. navigateurL'écran est redessinéà partir du DOM mis à jour

Clique sur « Suivre un clic pas à pas » : on va suivre le premier affichage de TaskFlow, puis ce qui se passe quand l'utilisateur coche « Installer Vite ».

Tu n'écris que les étapes 1, 2 et le gestionnaire de clic. React s'occupe des étapes 3 et 4, le navigateur de l'étape 5.

Pourquoi React compare-t-il au lieu de tout reconstruire ? Parce que modifier le DOM coûte du temps, et que tout reconstruire ferait perdre au passage le texte en cours de saisie, la position de défilement ou le champ actif.

À retenir

Tu entendras parler de « DOM virtuel ». C'est le nom donné à la description légère de l'écran que tes composants renvoient (étape 2) et que React compare (étape 3), avant de toucher au vrai DOM (étape 4).

Quelle version de React ?

Ce cours suit React 19 ; la version stable actuelle est la 19.3, publiée le 9 septembre 2026. Les fondamentaux présentés ici n'ont pas bougé depuis l'arrivée des hooks en 2019. Dans de vieux projets ou tutoriels, tu croiseras des composants écrits sous forme de classes, l'outil create-react-app (déprécié depuis février 2025) ou ReactDOM.render (supprimé en React 19). On verra comment les reconnaître.

En bref

  • Le navigateur transforme le HTML en DOM, un arbre d'objets, et dessine l'écran à partir de lui.
  • Avec React, tu ne modifies pas le DOM : tu modifies les données, tes composants décrivent l'écran, React applique les différences.
  • Comme tout part des mêmes données, plusieurs zones de l'écran ne peuvent plus se contredire.

Qu'est-ce que le DOM ?

Le HTML est du texte, lu une fois. Le DOM est l'arbre d'objets construit à partir de ce texte. Il existe avec ou sans React : React se contente de le modifier pour toi.

Dans React, une donnée change et l'écran doit suivre. Que fais-tu ?

C'est le cycle du schéma : données, description, comparaison, modification du DOM, affichage. Tu n'interviens qu'au début (les données) et dans la description (tes composants).

7. Vérité, égalité

Piège

8. Valeur ou référence : la notion la plus importante pour React

Les valeurs simples (nombres, chaînes, booléens) sont copiées. Les objets et les tableaux, eux, sont partagés : une variable ne contient pas l'objet, elle contient son adresse en mémoire.

u1 → objet n°1 u2 → objet n°1 u3 → objet n°2
objet n°1{ name: "Grace" }
objet n°2{ name: "Grace" }

Analogie

Une variable qui « contient » un objet est comme un papier où est notée l'adresse d'une maison. Copier la variable, c'est recopier l'adresse sur un deuxième papier : il y a toujours une seule maison. Si quelqu'un repeint la maison, tous les détenteurs de l'adresse la verront repeinte. Pour avoir deux maisons, il faut en construire une seconde.

=== sur deux objets compare les adresses, pas l'intérieur des maisons. React compare de cette façon : retiens cette image, le module 05 en dépend.

12. L'asynchrone : Promise, async, await

Un appel réseau prend du temps. JavaScript ne bloque pas en l'attendant : il te donne tout de suite une Promise, une promesse de résultat futur, et continue son travail.

Analogie

Au pressing, on te remet un ticket tout de suite ; les vêtements, tu les récupères plus tard. La Promise est le ticket. await veut dire « j'attends ici que le ticket soit honoré avant de continuer cette fonction ».

Côté backend

Une Promise joue le rôle d'une Task<T> en C# ou d'une coroutine en Python, et async / await s'utilisent de la même façon. Différence importante : fetch ne lève une exception qu'en cas d'échec réseau. Un 404 ou un 500 renvoie une réponse normale ; c'est à toi de tester res.ok.

Le projet, fichier par fichier

Clique sur un fichier pour voir à quoi il sert, si tu y toucheras, et à quoi il ressemble.

mon-app/ src/

index.html tu y touches rarement

La seule page HTML de l'application. Elle est presque vide : une div avec l'identifiant root, et une balise script qui charge main.jsx. Toute l'interface sera construite par React à l'intérieur de cette div.

Tu y modifieras le titre de l'onglet, la langue ou l'icône. Jamais le contenu de la page : c'est le travail de React.

package.json tu y touches souvent

La carte d'identité du projet, l'équivalent d'un pyproject.toml ou d'un .csproj. Elle liste les bibliothèques utilisées et les commandes disponibles.

  • scripts : les commandes que tu lances avec npm run. npm run dev exécute vite.
  • dependencies : ce dont l'application a besoin pour fonctionner. react fournit les composants et les hooks ; react-dom fait le lien avec le DOM du navigateur. Ce sont deux paquets séparés parce que React sait aussi produire des applications mobiles, avec un autre « traducteur » (React Native).
  • devDependencies : les outils utilisés seulement pendant le développement (Vite, le linter). Ils ne partent pas chez l'utilisateur.
  • ^19.3.0 : « 19.3.0 ou toute version compatible plus récente, sans passer à 20 ».

Tu n'édites pas les versions à la main : npm install nom-du-paquet ajoute la ligne pour toi.

package-lock.json tu n'y touches jamais

Généré automatiquement par npm install. Il note la version exacte de chaque paquet installé, y compris les dépendances de tes dépendances, pour que tous les membres de l'équipe et le serveur de build installent exactement la même chose.

C'est l'équivalent d'un poetry.lock ou d'un packages.lock.json. On le commite dans Git, mais on ne l'édite jamais à la main. Il fait souvent plusieurs milliers de lignes : c'est normal.

vite.config.js tu y touches rarement

La configuration de Vite. Le plugin react() lui apprend à comprendre le JSX. Un ajout très utile pour un dev backend : le proxy, qui redirige pendant le développement les appels /api vers ton serveur local.

Avec ce proxy, ton front (port 5173) et ton API (port 8000) se comportent comme s'ils étaient sur le même serveur : pas de configuration CORS pendant le développement.

eslint.config.js tu y touches rarement

La configuration d'ESLint, l'outil qui analyse ton code et signale les erreurs probables, comme ruff ou les analyseurs Roslyn. Le projet inclut les règles react-hooks, qui vérifient les règles des hooks (module 09) et les dépendances des effets (module 08).

Installe l'extension ESLint de ton éditeur : les avertissements apparaissent soulignés pendant que tu tapes. Ils t'éviteront beaucoup de bugs React.

.gitignore tu y touches rarement

La liste de ce que Git doit ignorer. On y trouve notamment node_modules (trop gros, se réinstalle avec npm install) et dist (se régénère avec npm run build). Si tu crées un fichier .env.local pour des réglages locaux, il doit y figurer aussi.

node_modules/ tu n'y touches jamais

Le dossier où npm install télécharge toutes les bibliothèques, comme un environnement virtuel Python. Il est énorme (des centaines de mégaoctets n'ont rien d'anormal) et ne se commite pas.

Si le projet se comporte bizarrement après un changement de branche, le remède classique : supprimer node_modules et relancer npm install.

public/ tu y touches rarement

Les fichiers servis tels quels, sans transformation, à la racine du site : public/favicon.svg sera accessible à l'adresse /favicon.svg. On y met le favicon, un robots.txt, des fichiers qu'on référence par leur URL fixe.

Pour les images utilisées dans tes composants, préfère src/assets/ (voir ce dossier).

src/main.jsx tu y touches rarement

Le point d'entrée du JavaScript, l'équivalent de main.py ou de Program.cs. Il ne fait qu'une chose : brancher React sur la div#root de index.html et y afficher le composant App.

Dans un vrai projet, c'est aussi là qu'on enveloppe App dans les « providers » globaux (authentification, thème, cache de données). On le détaille juste en dessous.

src/App.jsx tu y touches souvent

Le composant racine : le premier de l'arbre, celui qui contient tous les autres. C'est là que tu commences à écrire ton application. Le modèle Vite y met une petite démo avec un compteur, que tu peux effacer.

App.css, index.css tu y touches souvent

Des feuilles de style ordinaires. index.css contient les styles globaux (police, couleurs de fond) et est importé dans main.jsx ; App.css contient les styles de App.

Particularité : on importe un fichier CSS depuis le JavaScript (import "./App.css"). Vite se charge de l'injecter dans la page. Dans les vrais projets, tu verras aussi Tailwind (des classes utilitaires) ou des fichiers *.module.css (styles limités à un composant).

src/assets/ tu y touches souvent

Les images et fichiers utilisés par ton code. On les importe comme un module, et Vite fournit leur URL finale (optimisée, avec un nom unique pour le cache).

Différence avec public/ : un fichier de assets/ est vérifié et optimisé au build (un import cassé provoque une erreur) ; un fichier de public/ est copié sans contrôle.

dist/ généré, jamais modifié

Créé par npm run build. Il contient la version finale : un index.html, et quelques fichiers JavaScript et CSS compressés. Ton JSX a disparu, traduit en JavaScript standard.

C'est ce dossier qu'on déploie : sur nginx, sur un CDN, ou dans le dossier de fichiers statiques de ton application ASP.NET ou FastAPI. Il ne contient que des fichiers statiques : pas besoin de Node.js en production.

Composants et JSX

Objectifs

  • Écrire un composant et l'utiliser.
  • Comprendre ce que devient le JSX, pour que ses règles deviennent logiques.
  • Connaître les dix règles de JSX, avec les messages d'erreur associés.
  • Découper un écran en composants.

Un composant, c'est une fonction

Trois choses font d'une fonction un composant :

  1. c'est une fonction JavaScript ordinaire ;
  2. son nom commence par une majuscule (Greeting, pas greeting) ;
  3. elle renvoie du JSX, c'est-à-dire la description de ce qu'il faut afficher (ou null pour ne rien afficher).

On l'utilise ensuite comme une balise : <Greeting />. Quand React rencontre cette balise, il appelle la fonction Greeting() et regarde ce qu'elle renvoie. Ici, App l'utilise deux fois : React appelle donc Greeting deux fois, et le titre apparaît deux fois.

Qu'est-ce que JSX, exactement ?

JSX ressemble à du HTML, mais ce n'en est pas. Avant d'arriver dans le navigateur, Vite le traduit en JavaScript : chaque balise devient un appel de fonction. Cet appel produit un petit objet qui décrit l'élément voulu (React l'appelle un « élément »). Enfin, React utilise ces descriptions pour créer ou modifier le DOM.

Choisis un exemple et suis-le à travers les quatre étapes :

Les attributs deviennent les clés d'un objet JavaScript. C'est pour ça qu'on écrit className : class est un mot réservé de JavaScript.

Les balises enfants deviennent des appels imbriqués, rangés dans children. Le JSX décrit un arbre ; l'objet produit est un arbre ; le DOM final est un arbre.

Ce qui est entre accolades est copié tel quel dans l'appel de fonction : c'est du JavaScript évalué. Voilà pourquoi on ne peut y mettre qu'une expression (règle 3).

Avec une minuscule (<h1>), Vite écrit la chaîne "h1" : une balise HTML. Avec une majuscule (<Greeting>), il écrit la variable Greeting : ta fonction. C'est la règle 7. Note aussi que le composant n'apparaît pas dans le DOM : seul ce qu'il renvoie y arrive.

Les règles de JSX, une par une

Presque toutes les règles découlent de ce que tu viens de voir : le JSX devient des appels de fonctions et des objets JavaScript. Pour chaque règle : ce qu'elle dit, pourquoi elle existe, un exemple faux puis juste, et le message que tu verras si tu l'oublies.

Règle 1 Un composant renvoie un seul élément racine

Pourquoi ? Une fonction ne renvoie qu'une seule valeur. Deux balises côte à côte, ce seraient deux appels jsx(...) à renvoyer en même temps : impossible. Il faut les regrouper dans un parent.

<>…</> s'appelle un Fragment : il regroupe sans rien ajouter dans le DOM. On aurait pu utiliser une div, mais une balise inutile peut casser une mise en page (une grille, un tableau, une liste ul/li).

Message : Adjacent JSX elements must be wrapped in an enclosing tag

Règle 2 Toutes les balises se ferment

Pourquoi ? Le traducteur doit savoir exactement où se termine chaque appel. Le HTML tolère <br> ou <img> sans fermeture ; JSX non. Une balise sans contenu se ferme elle-même avec />.

Message : Expected corresponding JSX closing tag for <img>

Règle 3 Les accolades ouvrent une fenêtre sur JavaScript

Dans du JSX, tout est du texte fixe, sauf ce qui est entre accolades { } : là, c'est du JavaScript, évalué au moment du rendu. Les accolades peuvent apparaître à deux endroits : dans le contenu d'une balise, et comme valeur d'un attribut.

Pourquoi seulement des expressions ? Le contenu des accolades atterrit tel quel comme argument d'un appel de fonction (onglet « Une expression » ci-dessus). On peut écrire f(a ? b : c), mais pas f(if (a) b). Une expression produit une valeur (a + b, x ? y : z, list.map(...)) ; une instruction fait quelque chose (if, for, const) et ne passe pas.

Règle 4 Un attribut prend des guillemets OU des accolades, jamais les deux

  • Guillemets pour une chaîne fixe : alt="Photo de profil".
  • Accolades pour tout le reste : une variable, un nombre, un booléen, une fonction, un objet.

Règle 5 Les noms d'attributs s'écrivent en camelCase

Pourquoi ? Les attributs deviennent les clés d'un objet JavaScript, et React utilise les noms des propriétés du DOM, qui sont en camelCase (tabIndex, et non tabindex).

Les propriétés CSS passent en camelCase (font-size devient fontSize) et un nombre seul est compris comme des pixels. En pratique, on préfère des classes CSS et on garde style pour des valeurs calculées (une largeur en pourcentage, une couleur choisie par l'utilisateur).

Pourquoi ? Le traducteur se fie à la première lettre. <button> devient la chaîne "button" (une balise HTML) ; <Button> devient la variable Button (ta fonction, qui doit donc être importée).

Pourquoi ? JavaScript ajoute automatiquement un point-virgule après un return suivi d'un retour à la ligne. Le composant renvoie alors undefined et le JSX en dessous n'est jamais atteint.

Règle 10 Le texte est protégé automatiquement

Tout ce que tu affiches entre accolades est traité comme du texte, jamais comme du HTML. Si un utilisateur malveillant saisit un titre de tâche contenant une balise <script>, elle s'affichera telle quelle, sans être exécutée.

Pourquoi une variable ordinaire ne suffit pas

Deux problèmes :

  1. Rien ne déclenche un nouvel affichage. React ne surveille pas tes variables. Il ne refait le rendu que si on le lui demande.
  2. Même s'il refaisait le rendu, la fonction serait rappelée depuis le début, et let count = 0 remettrait tout à zéro.

Ton composant est un employé qui perd la mémoire à chaque appel : il recommence son travail de zéro à chaque rendu. useState lui donne un casier à son nom, géré par React. À chaque rendu, il ouvre son casier et y trouve la dernière valeur. Et changer le contenu du casier passe par un guichet (le setter), qui prévient React de refaire le travail.

L'état est une photo prise au moment du rendu

Pendant un rendu, count est une constante : une photo de la valeur à cet instant. Le setter ne modifie pas la photo ; il prépare la valeur du rendu suivant. Règle simple : si la nouvelle valeur dépend de l'ancienne, passe une fonction au setter (c => c + 1). React lui donnera toujours la valeur la plus récente.

React regroupe aussi tous les appels de setters d'un même événement en un seul nouveau rendu (le batching). Trois setX dans un clic, c'est un seul rendu.

Objets et tableaux : pourquoi il faut créer une copie

C'est la partie qui surprend le plus. Prenons-la en cinq étapes, en nous appuyant sur la notion de référence vue au module 01.

Étape 1 · Une variable ne contient pas l'objet, elle pointe vers lui

Quand l'état contient un objet, la variable user ne contient pas l'objet lui-même mais son adresse en mémoire. Comme un papier sur lequel est notée l'adresse d'une maison.

user → objet n°1
objet n°1{ name: "Ada", email: "ada@mail.com" }

Étape 2 · Comment React décide de refaire l'affichage

Quand tu appelles setUser(x), React compare x à la valeur actuelle avec Object.is, l'équivalent de ===. Pour des objets, cette comparaison regarde l'adresse, pas le contenu :

  • même adresse → « rien n'a changé » → React ne fait rien ;
  • adresse différente → « quelque chose a changé » → React refait le rendu.

Pourquoi ne pas comparer le contenu ? Parce que fouiller l'intérieur de gros objets à chaque mise à jour serait lent. Comparer deux adresses est instantané.

Étape 4 · Le spread : une photocopie avec une correction

Lis cette ligne en trois temps :

  1. { } : construis un nouvel objet, donc une nouvelle adresse.
  2. ...user : recopie dedans toutes les propriétés de user (name: "Ada", email: …).
  3. name: "Grace" : puis remplace name. La dernière valeur écrite gagne.

Résultat : { name: "Grace", email: "ada@mail.com" }, à une nouvelle adresse. L'ordre compte : { name: "Grace", ...user } recopierait user par-dessus et name redeviendrait « Ada ».

Étape 5 · Les objets imbriqués : copier chaque niveau modifié

Le spread ne copie qu'un seul niveau. Si user contient un objet address, la copie recopie l'adresse de cet objet intérieur, pas l'objet lui-même : les deux versions partagent la même address.

user → objet n°1 copie → objet n°2
objet n°1{ name: "Ada", address: → n°3 }
objet n°2{ name: "Ada", address: → n°3 }
objet n°3 (partagé !){ city: "Paris" }

Règle pratique : sur le chemin qui mène à la valeur modifiée, chaque objet doit être recopié. Le reste peut être partagé sans danger, puisqu'on n'y touche pas.

        Le cycle de rendu : ce qui se passe vraiment

        Objectifs

        • Savoir ce qui déclenche un rendu, et ce que React fait ensuite.
        • Comprendre pourquoi un composant doit rester « pur ».
        • Comprendre que chaque rendu garde ses propres valeurs, comme une photo.
        • Décider où placer un état dont plusieurs composants ont besoin.
        • Savoir quand React conserve l'état d'un composant, et quand il l'efface.

        Ce module est le plus utile pour débugger : la plupart des bugs React viennent d'une idée fausse sur le moment où le code s'exécute. Au module 00, on a vu le cycle complet en six étapes. Ici, on regarde de près ce qui se passe entre « une donnée change » et « l'écran est à jour ».

        « Rendre » ne veut pas dire « dessiner »

        Le mot prête à confusion. En React, rendre un composant, c'est simplement appeler sa fonction pour savoir quel JSX elle renvoie. Rien ne change encore à l'écran. Le travail se fait en quatre temps :

        1. Déclenchementle premier affichage, ou un setter appelé quelque part (setTasks(...)).
        2. RenduReact appelle tes composants. Ils calculent et renvoient leur JSX. C'est un calcul, sans effet visible.
        3. CommitReact compare le nouveau JSX à l'ancien et applique les différences au DOM.
        4. Effetsune fois l'écran à jour, React exécute les useEffect concernés (module 08).

        Analogie

        Un architecte et un chantier. Le rendu, c'est dessiner le plan : on peut en dessiner dix versions, rien ne bouge dans la maison. Le commit, ce sont les travaux : on ne casse que les murs qui diffèrent entre l'ancien plan et le nouveau. Les effets viennent ensuite, une fois la pièce terminée : brancher la box Internet, par exemple.

        Qu'est-ce qui déclenche un nouveau rendu ?

        Un composant se re-rend dans trois cas, et seulement ceux-là :

        1. Son propre état change : un de ses setters est appelé avec une nouvelle valeur.
        2. Son parent se re-rend : par défaut, un rendu descend vers tous les enfants, même si leurs props n'ont pas changé.
        3. Un contexte qu'il lit change (module 10).

        Les props ne sont pas une quatrième cause : si les props d'un composant changent, c'est forcément que son parent s'est re-rendu. Essaie sur l'arbre de TaskFlow : chaque bouton appelle un setter dans un composant différent.

        Un rendu doit être pur

        Une fonction est pure si elle respecte deux règles :

        • mêmes entrées, même résultat : avec les mêmes props, le même état et le même contexte, le composant renvoie toujours le même JSX ;

            useEffect : se synchroniser avec l'extérieur

            Objectifs

            • Comprendre à quoi sert un effet, et ce qui le distingue d'un gestionnaire d'événement.
            • Savoir quand un effet s'exécute, selon son tableau de dépendances.

            Le problème : faire quelque chose parce qu'on est affiché

            Jusqu'ici, notre code se rangeait dans deux cases :

            • le rendu : calculer le JSX à partir des props et de l'état. Il doit rester pur (module 07) ;
            • les gestionnaires d'événements : réagir à une action précise de l'utilisateur (un clic, un envoi).

            Certains besoins ne rentrent dans aucune des deux. Le salon de discussion doit se connecter au serveur dès qu'il est affiché, pas quand on clique. Le titre de l'onglet doit afficher le nombre de messages non lus tant que la page est ouverte. Un minuteur doit tourner pendant que le chronomètre est à l'écran.

            Ces besoins ont un point commun : ils concernent un système extérieur à React (le réseau, le navigateur, un minuteur, un widget tiers) qu'il faut garder d'accord avec ce qui est affiché. C'est le rôle d'un effet.

            Analogie

            Une chambre d'hôtel. Quand tu entres, tu allumes la lumière. Quand tu pars, tu l'éteins. Si tu changes de chambre, tu éteins l'ancienne avant d'allumer la nouvelle. Un effet suit exactement ces trois temps : une mise en place, un nettoyage, et on recommence quand la « chambre » (une dépendance) change.

            Anatomie d'un effet

            Lis cet effet comme une phrase : « tant que ce composant est affiché avec ce roomId, il doit y avoir une connexion à ce salon ». Tu décris l'état dans lequel doit être l'extérieur, et React s'occupe de connecter et déconnecter au bon moment.

            Quand l'effet s'exécute-t-il ?

            Un effet ne s'exécute jamais pendant le rendu. Il passe en dernier, une fois l'écran à jour :

            1. RenduReact appelle ChatRoom, qui renvoie son JSX. useEffect ne fait qu'enregistrer la fonction pour plus tard.
            2. CommitReact met le DOM à jour : le titre « Salon général » existe.
            3. Peinturele navigateur affiche l'écran. L'utilisateur voit déjà le salon.
            4. EffetReact exécute ta fonction : la connexion s'ouvre.

            Sur toute la vie du composant, voici ce que fait React avec l'effet du salon :

            rendueffet : connexion à « général »

            Re-rendu
            autre état modifié, roomId identique

            rendueffet ignoré : dépendances identiques

            Re-rendu

            À retenir · la règle des dépendances

            Toute valeur du composant utilisée dans l'effet (props, état, fonctions déclarées dans le composant) doit figurer dans le tableau. Tu ne choisis pas les dépendances : elles découlent du code de l'effet. La règle ESLint react-hooks/exhaustive-deps les vérifie pour toi.

            Le nettoyage

            Toute ressource ouverte dans un effet doit être refermée dans son nettoyage : connexion, abonnement, minuteur, écouteur d'événement. Sinon, les ressources s'accumulent à chaque changement : deux connexions ouvertes, deux minuteurs qui tournent, des écouteurs en double.

            Côté backend

            La fonction de nettoyage joue le rôle d'un bloc with (__exit__) ou d'un finally en Python, ou d'un using / Dispose() en C# : ce qui est ouvert doit être fermé, quoi qu'il arrive.

            StrictMode : pourquoi ton effet s'exécute deux fois

            Coche « StrictMode » dans la démo ci-dessus et réinitialise. Au montage, tu vois : effet, nettoyage, effet. En développement, React monte le composant, le démonte aussitôt, puis le remonte. C'est un test automatique : si ton effet a un nettoyage correct, l'utilisateur ne voit aucune différence (on se retrouve avec une seule connexion). S'il en manque un, le bug apparaît tout de suite, en développement, plutôt que des semaines plus tard en production.

            Piège

            Ne désactive pas StrictMode pour « corriger » un effet lancé deux fois. Le double appel n'est pas le problème : il révèle un nettoyage manquant. En production, l'effet ne s'exécute qu'une fois au montage.

                Extraire la logique dans un custom hook

                Un custom hook, c'est simplement une fonction dont le nom commence par use et qui appelle d'autres hooks. Rien de magique : React ne le traite pas différemment. Le préfixe use sert au linter, qui sait alors appliquer les règles des hooks à cette fonction.

                2. Le hookdes useState, des useEffect, d'autres hooks

                Suspense et lazy : déclarer les états de chargement

                Objectifs

                • Comprendre ce que veut dire « un composant suspend », étape par étape.

                Le problème : des isLoading partout

                Avec le motif du module 08, chaque composant qui charge quelque chose gère lui-même son chargement :

                Ça fonctionne, mais chaque composant répète les mêmes conditions, et l'écran affiche plusieurs indicateurs de chargement qui disparaissent un par un, dans un ordre imprévisible. Suspense propose de sortir cette question des composants.

                L'idée de Suspense

                Avec Suspense, un composant qui n'est pas prêt (son code ou ses données sont en cours de chargement) suspend : il signale à React qu'il attend. Le <Suspense> le plus proche au-dessus de lui affiche alors un contenu de remplacement, le fallback, à sa place.

                Analogie

                Au théâtre, le rideau reste baissé tant que le décor n'est pas en place. Les comédiens ne viennent pas un par un annoncer « je ne suis pas prêt ». <Suspense> est le rideau, fallback est ce qu'on projette dessus en attendant, et c'est toi qui décides où poser les rideaux.

                Comment ça marche, pas à pas

                1. React rend Commentscomme n'importe quel composant.
                2. Comments suspendses données ne sont pas prêtes : il signale à React qu'il attend une promesse.
                3. React remontejusqu'au <Suspense> le plus proche et affiche son fallback.
                4. La promesse se résoutles données arrivent ; React réessaie de rendre Comments.
                5. Le contenu remplace le fallbackcette fois, Comments a tout ce qu'il faut.

                Le composant lui-même ne contient plus que le cas où tout va bien. La question « que montre-t-on pendant l'attente ? » est réglée au-dessus de lui, une fois pour toute une zone.

                Côté backend

                C'est un await déclaratif. Le composant « attend » quelque chose, et c'est l'endroit où tu as placé <Suspense> qui décide de ce qu'on voit pendant l'attente, un peu comme un middleware qui encadre plusieurs routes.

                Ce qui peut faire suspendre un composant

                1. Un composant chargé avec lazy, dont le code n'est pas encore téléchargé.
                2. Des données lues via une source compatible Suspense : un framework comme Next.js, useSuspenseQuery de React Query, ou use(promesse) avec une promesse mise en cache.

                Piège

                Suspense ne détecte pas les données chargées dans un useEffect. L'effet s'exécute après l'affichage : au moment où React a rendu le composant, il n'y avait rien à attendre. Avec le motif du module 08, c'est ton propre isLoading qui gère l'affichage, et le fallback ne s'affiche jamais.

                Par défaut, Vite regroupe tout le code de l'application dans un seul fichier JavaScript, téléchargé à la première visite. Même l'utilisateur qui ne verra jamais le tableau de bord d'administration télécharge son code.

                use : lire une promesse

                React 19 fournit use, qui lit le résultat d'une promesse. Tant qu'elle n'est pas résolue, le composant suspend.

                Pourquoi le cache ? Au point 4 du schéma ci-dessus, React réessaie de rendre le composant. Si chaque rendu créait un nouveau fetch, il y aurait une nouvelle promesse à attendre à chaque essai, sans fin. La promesse doit donc être stable d'un rendu à l'autre. En pratique, c'est React Query ou le framework qui gère ce cache pour toi. Si la promesse est rejetée, l'erreur remonte à l'error boundary la plus proche (module suivant).

                    Voir la version corrigée

                    La version corrigée est plus courte, sans effet, et toujours juste dès le premier rendu. Un signe fréquent : quand du code React se simplifie en le corrigeant, c'est qu'on se rapproche du bon modèle.

                    Piège · sécurité

                    • Tout le code front est public. Une clé d'API placée dans le code React, y compris dans une variable VITE_…, finit dans le JavaScript téléchargé par le navigateur. Les secrets restent côté backend.
                    • dangerouslySetInnerHTML avec du contenu venu d'un utilisateur ouvre la porte aux failles XSS.
                    • Une validation côté front améliore l'expérience, mais ne protège rien : ton API doit tout revalider.

                    Apprendre avec l'IA

                    • Explique, puis reformule : demande une explication, réexplique avec tes mots, et demande à l'IA de corriger ta compréhension.
                    • Demande ce qui pourrait casser : « quels cas limites ce code ne gère-t-il pas ? »
                    • Fais écrire les tests : une proposition de tests avec Testing Library révèle souvent des comportements auxquels tu n'avais pas pensé.
                    • Demande la fiche d'identité d'un composant (module 15) : props, état, contextes et hooks, effets, affichage.
                    • Vérifie les affirmations sur les versions et les API dans la documentation officielle : c'est là que l'IA se trompe le plus souvent.

                    En bref

                    • Un bon prompt donne les versions, les fichiers, les contraintes, et demande un plan avant le code.
                    • Avance par petits pas : une modification, on lance, on lit le diff, on demande pourquoi, on commite.
                    • Relis avec la grille : effets inutiles, dépendances muselées, mutations, keys instables, APIs anciennes ou inventées, failles de sécurité.
