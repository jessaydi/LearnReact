Hooks · la boîte à outils

Les règles des hooks et les autres hooks que tu croiseras

Objectifs

  • Connaître les deux règles des hooks et comprendre pourquoi elles existent.
  • Savoir lire useRef, useMemo, useCallback, memo et useReducer.
  • Choisir le bon hook selon le besoin.

Les deux règles des hooks

  1. On appelle les hooks au premier niveau du composant : jamais dans un if, une boucle, une fonction imbriquée, ni après un return anticipé.
  2. On les appelle uniquement depuis un composant React ou depuis un custom hook (module 11).

Analogie

React ne connaît pas le nom de tes variables. Il range les hooks de chaque composant dans une liste, dans l'ordre d'appel : case 1, case 2, case 3. C'est comme des paramètres positionnels : si tu en sautes un, tous les suivants sont décalés. D'où l'erreur Rendered more hooks than during the previous render.

Une seule exception : use (module 12) peut s'appeler dans une condition. Le plugin ESLint react-hooks, installé dans les projets Vite, vérifie ces règles à ta place.

Vois une ref comme un champ privé d'une classe, qui ne notifie personne quand il change. Nouveauté de React 19 : un composant fonction reçoit ref comme une prop ordinaire. Dans du code plus ancien, tu verras forwardRef(...), qui servait au même usage.

useMemo, useCallback et memo : la mémoïsation

C'est l'équivalent d'un @lru_cache en Python ou d'un cache avec une clé : on ne recalcule que si les entrées changent.

À retenir

Depuis octobre 2025, le React Compiler (version 1.0 stable) mémoïse automatiquement composants et valeurs au moment du build. Pour du nouveau code, l'équipe React recommande de s'appuyer sur lui et de garder useMemo et useCallback comme échappatoires ponctuelles. Dans les projets existants et dans le code généré par une IA, tu en verras partout : sache les lire, n'en ajoute pas « au cas où ».

Pourquoi ne peut-on pas appeler useState dans un if ?

React associe les valeurs aux hooks par position : 1er appel, 2e appel… Un hook conditionnel décale tous les suivants d'un rendu à l'autre, et chaque hook récupère la valeur d'un autre.

Partager

Context API et useContext

Objectifs

  • Identifier le « prop drilling » et le remplacer par un contexte.
  • Créer, fournir et lire un contexte.
  • Écrire le motif de production : Provider + custom hook.
  • Savoir quand un contexte est une mauvaise idée.

Le problème : faire traverser des props

Les composants intermédiaires transportent une donnée qui ne les concerne pas. Sur cinq niveaux et trois données, ça devient pénible et fragile.

La solution en trois étapes

  • App · <ThemeContext value="dark">
    • Layout n'utilise pas le thème
      • Sidebar non plus
        • ThemeButton · useContext → "dark"
      • Header · useContext → "dark"

Analogie

Les props sont des câbles : il faut les tirer de pièce en pièce. Un contexte, c'est le Wi-Fi : le fournisseur émet, et tout composant « à portée » (en dessous dans l'arbre) se connecte sans câble. Si deux fournisseurs du même contexte sont imbriqués, c'est le plus proche qui gagne.

Côté backend

C'est de l'injection de dépendances avec une portée : un service scoped enregistré pour un sous-arbre, que n'importe quel composant de ce sous-arbre peut demander. Proche aussi de HttpContext en ASP.NET ou des contextvars en Python : une valeur ambiante, accessible sans la passer en paramètre.

Le motif de production : Provider + custom hook

Dans un vrai projet, tu trouveras presque toujours la même structure : un fichier qui exporte un composant Provider et un hook useXxx.

Avec le React Compiler activé, tu peux écrire ce fichier sans useCallback ni useMemo : il les ajoute pour toi.

Ce que coûte un contexte

Quand la valeur fournie change (par référence), tous les composants qui lisent ce contexte se re-rendent. Si tu écris value={{ user, logout }} sans mémoïsation, un nouvel objet est créé à chaque rendu du Provider, et tous les consommateurs se re-rendent à chaque fois. D'où le useMemo ci-dessus.

Bon usageMauvais usage
Thème, langue, utilisateur connecté, droits, notifications : global et peu changeant.Éviter de passer une prop sur un ou deux niveaux : passe-la, tout simplement.
Données dont beaucoup de composants éloignés ont besoin.Mettre en cache les données du serveur : c'est le rôle de React Query.
Une famille de composants qui coopèrent (des onglets et leurs panneaux).Une valeur qui change à chaque frappe ou à chaque frame : tout se re-rend.

Avant de créer un contexte, essaie aussi la composition : passer directement le JSX prêt à l'emploi évite de faire traverser une donnée.

Piège

  • Provider oublié : useContext renvoie silencieusement la valeur par défaut. D'où le garde-fou qui lève une erreur dans useAuth.
  • Provider placé trop bas : useContext ne regarde qu'au-dessus. Un composant au-dessus ou à côté du Provider ne voit pas sa valeur.

Exercice

Crée un contexte de langue ("fr" ou "en") avec un LanguageProvider et un hook useLanguage qui renvoie la langue et une fonction pour basculer. Un bouton bascule la langue ; un composant Greeting affiche « Bonjour » ou « Hello ».

Voir la solution

Un composant appelle useContext(ThemeContext), mais aucun fournisseur n'existe au-dessus de lui. Que reçoit-il ?

Sans fournisseur au-dessus, React renvoie la valeur par défaut, sans prévenir. C'est pour ça qu'on crée souvent le contexte avec null et qu'on lève une erreur explicite dans le custom hook.

Réutiliser

Custom hooks : extraire et réutiliser de la logique

Objectifs

  • Extraire une logique avec état dans une fonction useXxx.
  • Comprendre qu'un custom hook partage de la logique, pas de l'état.
  • Lire et écrire les hooks qu'on retrouve dans tous les projets.

Avant / après

Si un bouton « Enregistrer » a aussi besoin de savoir si on est en ligne, tu ne vas pas copier ces quinze lignes. Tu les extrais :

Un custom hook, c'est une fonction dont le nom commence par use et qui appelle d'autres hooks. Rien de magique : React ne le traite pas différemment d'une fonction. Le préfixe use sert au linter, qui applique alors les règles des hooks.

À retenir

Un custom hook partage de la logique, pas de l'état. StatusBar et SaveButton ont chacun leur propre isOnline. Pour partager un même état entre plusieurs composants, il faut le remonter ou passer par un contexte.

Côté backend

En termes d'injection de dépendances, un custom hook a une durée de vie transient : chaque composant qui l'appelle obtient sa propre instance. Un contexte, lui, ressemble à un service scoped partagé par tout un sous-arbre.

Les hooks qu'on retrouve partout

Regarde la forme de ce que renvoie useFetch : { data, isLoading, error }. React Query renvoie à peu près la même chose avec useQuery, en ajoutant le cache, la déduplication des requêtes, les nouvelles tentatives et l'invalidation. Tu reconnaîtras la forme.

Bien concevoir un custom hook

  • Nomme-le par son intention : useOnlineStatus, useCurrentUser. Évite les noms de cycle de vie comme useMount.
  • Renvoie un tableau pour deux valeurs (comme useState), un objet au-delà, pour que l'appelant choisisse ce qu'il lit.
  • Une fonction qui n'appelle aucun hook n'est pas un hook : nomme-la normalement (formatDate, pas useFormatDate).
  • Pour lire un projet, traite chaque custom hook comme une boîte noire : qu'entre-t-il, que sort-il ? N'ouvre le fichier que si le bug semble venir de là.

Exercice

Écris useCounter(initial = 0, step = 1) qui renvoie { count, increment, decrement, reset }. Utilise-le dans deux compteurs indépendants.

Voir la solution

Deux composants appellent useToggle(). On bascule le premier. Que devient le second ?

Chaque appel d'un custom hook crée son propre useState. Pour un état partagé, remonte-le chez un parent commun ou place-le dans un contexte.
