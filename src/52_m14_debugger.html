Pratique

Débugger une application React

Objectifs

  • Savoir ce que montre chaque outil : console, React DevTools, onglet Réseau, points d'arrêt.
  • Mener une enquête avec les DevTools, sur un cas concret.
  • Suivre une méthode reproductible au lieu de tâtonner.
  • Reconnaître les messages d'erreur et les symptômes classiques, et leur cause.

La boîte à outils

OutilLa question à laquelle il répond
Console du navigateur (F12)Y a-t-il une erreur ? Les erreurs sont en rouge, les avertissements de React en jaune. Lis la component stack sous l'erreur : elle dit dans quel composant c'est arrivé.
React DevTools, onglet ComponentsQue contient ce composant ? Ses props, son état, ses hooks, les contextes qu'il lit, et qui l'a rendu.
React DevTools, onglet ProfilerPourquoi c'est lent ? Quels composants se sont rendus pendant une interaction, combien de temps, et pourquoi (option « Record why each component rendered »).
Réglage Highlight updatesQui se re-rend ? Les composants qui se re-rendent clignotent à l'écran, comme dans la démo du module 07.
Onglet Réseau (Network)Que dit vraiment le backend ? La requête est-elle partie, avec quel statut, quel corps de réponse, une erreur CORS ?
Points d'arrêt (onglet Sources, ou l'instruction debugger;)Que valent les variables à cet instant ? Vite fournit les source maps : tu débugges ton code d'origine, pas le code compilé.

Les React DevTools sont une extension pour Chrome, Firefox et Edge. Une fois installée, deux onglets apparaissent dans les outils de développement : Components et Profiler.

Une enquête avec les DevTools

Voici un bug signalé dans TaskFlow : « La tâche Coder est marquée terminée en base, mais l'écran l'affiche à faire, et le compteur dit 3 au lieu de 2. » Les DevTools ci-dessous sont simulés, mais ils montrent les mêmes informations que les vrais. Clique sur les composants, puis sur l'onglet Network, et cherche la cause avant de lire la solution.

Démo · des React DevTools simulés

TaskFlow3 tâches restantes

  • Lire
  • Coder
  • Tester

GET /api/tasks 200 OK 48 ms

Response

[
  { "id": 1, "title": "Lire",   "is_done": false },
  { "id": 2, "title": "Coder",  "is_done": true },
  { "id": 3, "title": "Tester", "is_done": false }
]
Voir la solution de l'enquête
  1. Le composant fautif : TaskItem key="2" affiche une case décochée. Ses props contiennent task: { id: 2, title: "Coder", is_done: true }. La donnée est là, mais sous le nom is_done.
  2. Le code du composant lit task.done, qui vaut undefined : la case est décochée. Même cause pour le compteur, qui filtre sur !t.done.
  3. L'onglet Network confirme : le backend Python renvoie du snake_case (is_done), le front attend done. Aucune erreur nulle part, juste un contrat mal aligné.
  4. La correction : aligner le contrat. Soit le backend renvoie done (un alias Pydantic, par exemple), soit la couche api/ du front traduit les champs à un seul endroit :

Côté backend

Beaucoup de « bugs React » sont des écarts de contrat avec l'API : ASP.NET sérialise en camelCase par défaut (isDone), une API Python renvoie souvent du snake_case (is_done). Le front lit un champ qui n'existe pas, reçoit undefined, et n'affiche rien, sans aucune erreur. Le premier réflexe : ouvrir l'onglet Réseau et lire la vraie réponse.

Où placer un console.log ?

Un console.log ne dit pas la même chose selon l'endroit où tu le places, parce que ces endroits ne s'exécutent pas au même moment (module 07) :

Placé…Il s'affiche…Utile pour savoir…
dans le corps du composant, avant le returnà chaque rendu (deux fois en développement)avec quelles props et quel état le composant se rend, et combien de fois
dans un useEffectaprès l'affichage, quand les dépendances changentsi l'effet tourne trop souvent, ou pas du tout
dans un gestionnaire (onClick…)au moment de l'actionsi le clic arrive bien, et avec quelles valeurs
dans une fonction de api/à chaque appel réseauce qui part vers le backend et ce qui revient

Astuce : console.log({ tasks, filter }) affiche les valeurs avec leur nom, et console.table(tasks) affiche une liste d'objets sous forme de tableau.

Une méthode en cinq étapes

  1. Reproduiretrouver les étapes exactes qui déclenchent le bug.
  2. Localiserquel composant affiche la mauvaise chose ? (sélecteur des DevTools)
  3. Inspecterses props et son état sont-ils corrects ?
  4. Corrigerune hypothèse, une modification minimale.
  5. Vérifierle bug a disparu, rien d'autre n'a cassé, la console est propre.

L'étape 3 est le cœur du diagnostic. Grâce au flux à sens unique (module 04), chaque réponse t'envoie dans une direction précise :

Aide au diagnostic · l'écran affiche une valeur fausse

    Sélectionne le composant qui affiche la mauvaise chose. Ses props sont-elles justes ?

    Remonte au composant qui fournit cette prop (« rendered by » dans les DevTools). La valeur vient-elle de l'API ?

    Et son état (section « hooks » des DevTools) est-il juste ?

    Ouvre l'onglet Réseau

    Compare la réponse réelle avec ce que le front attend : nom des champs, types ("true" au lieu de true), valeurs null. Si la réponse est fausse, le bug est côté backend ; si elle est juste, il est dans la couche api/ ou dans la façon de la stocker.

    Pose la même question au parent

    Ouvre le composant parent, le hook ou le provider qui produit la valeur, et recommence le diagnostic à ce niveau. Le bug est quelque part sur ce chemin.

    Cherche qui écrit cet état

    Recherche tous les appels au setter (setTasks) ou au dispatch. Un console.log ou un point d'arrêt dans chaque gestionnaire te dira lequel écrit la mauvaise valeur. Vérifie aussi les mutations (module 05).

    Le bug est dans ce composant

    Props et état sont justes : c'est le calcul ou le JSX. Un nom de champ, une condition, un && avec un 0. Ajoute un console.log des valeurs calculées juste avant le return.

    En bref

    • Console pour les erreurs, DevTools pour les props et l'état, Réseau pour la vérité du backend, points d'arrêt pour les valeurs à un instant précis.
    • Méthode : reproduire, localiser, inspecter, corriger, vérifier.
    • Props fausses : remonte vers le parent. État faux : cherche qui l'écrit. Tout est juste : le bug est dans le calcul ou le JSX.

    Exercice · chasse aux bugs

    Ce composant contient cinq bugs. Trouve-les avant de regarder la solution.

    Voir la solution
    1. useState() vaut undefined : tasks.filter plante au premier rendu. Initialiser avec [].
    2. L'effet utilise userId mais ne le déclare pas : changer d'utilisateur n'a aucun effet. Ajouter [userId] et un drapeau ignore contre les réponses périmées.
    3. push modifie le tableau sur place, et setTasks(tasks) passe la même adresse : pas de nouvel affichage. Créer un nouveau tableau.
    4. onClick={setFilter("todo")} appelle le setter pendant le rendu : Too many re-renders. Passer une fonction.
    5. key={i} sur une liste qui sera filtrée : utiliser t.id.

    Un composant affiche un mauvais nom. Dans les DevTools, sa prop user contient déjà ce mauvais nom. Où cherches-tu ?

    Si la prop est déjà fausse, le composant ne fait qu'afficher ce qu'on lui donne. Remonte le flux de données : parent, puis contexte ou hook qui la produit, puis la réponse réseau.

    Un champ s'affiche vide, sans aucune erreur dans la console. Quel est ton premier réflexe ?

    Lire une propriété qui n'existe pas renvoie undefined sans erreur, et React n'affiche rien pour undefined. Un écart de nom entre le backend et le front est la cause la plus fréquente.
