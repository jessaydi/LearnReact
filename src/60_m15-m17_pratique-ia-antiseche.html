Pratique

Lire un projet inconnu et y ajouter une fonctionnalité

Objectifs

  • Savoir dans quel ordre lire un projet React existant.
  • Suivre une donnée de l'écran jusqu'à l'API.
  • Ajouter une fonctionnalité en choisissant le bon endroit pour l'état.

L'ordre de lecture

  1. package.jsonidentifie la pile technique avant de lire une seule ligne de code.
  2. main.jsxles providers globaux disent quels services sont disponibles partout.
  3. Les routesla carte URL → page : les écrans de l'application.
  4. Une pagesuis une donnée de bout en bout, de l'écran à l'API.

DépendanceCe qu'elle t'apprend

2. Lire les providers de main.jsx

Côté backend

Cette pile de providers joue le rôle de ton Program.cs : l'enregistrement des services et l'ordre du pipeline. En la lisant, tu sais ce que n'importe quel composant peut demander.

3. Lire les routes

C'est l'équivalent de ta table de routes ou de tes contrôleurs : chaque URL pointe vers un composant de page. La syntaxe exacte varie selon la bibliothèque et sa version, mais on la reconnaît toujours.

4. Suivre une donnée

Exemple : « le compteur de tâches de l'en-tête affiche un mauvais nombre ».

  1. Trouver le composant : sélecteur des DevTools sur le compteur, ou recherche du texte affiché (« tâches restantes ») dans tout le projet.
  2. D'où vient la valeur ? D'une prop : remonte au parent. De useContext ou d'un useXxx() : ouvre le provider ou le hook. D'un useQuery ou d'un fetch : regarde la requête dans l'onglet Réseau.
  3. Qui la modifie ? Cherche les appels au setter (setTasks), au dispatch ou à la mutation.

À retenir · la fiche d'identité d'un composant

Pour comprendre n'importe quel composant, réponds à cinq questions :

  1. Quelles props reçoit-il ?
  2. Quel état possède-t-il ?
  3. Quels contextes ou hooks utilise-t-il ?
  4. Quels effets lance-t-il ?
  5. Qu'affiche-t-il, et sous quelles conditions ?

À retenir · avant de commiter

  • La console est propre : aucune erreur, aucun avertissement de key.
  • Aucun état n'est modifié sur place.
  • Les tableaux de dépendances sont complets et le linter ne signale rien.
  • Aucune valeur dérivable n'est stockée dans un état ni calculée dans un effet.
  • Les cas limites sont gérés : liste vide, chargement, erreur.
  • Tu as suivi les conventions déjà présentes dans le projet.

Exercice

Reprends le TodoApp du module 05. Découpe-le en trois composants frères sous un même parent : Header (affiche le nombre de tâches restantes), AddTaskForm et TaskList. Ajoute un bouton « Tout cocher » dans Header. Où vit l'état ?

Voir la solution

Les trois composants ont besoin des tâches : l'état vit chez leur parent commun, qui passe les données et des callbacks.

Remarque : le brouillon draft reste local à AddTaskForm, car personne d'autre n'en a besoin. Place l'état le plus bas possible.

La liste des tâches vient de l'API et trois pages l'affichent. Où la garder ?

Les données serveur ont des besoins propres : cache partagé, rafraîchissement, invalidation après une modification. C'est exactement le rôle de React Query. Plusieurs copies dans des états locaux finissent par diverger.

Méthode

L'IA comme copilote, sans perdre le contrôle

Objectifs

  • Donner à l'IA le contexte qui produit du bon code React.
  • Relire le code généré avec une grille de signaux d'alerte.
  • Utiliser l'IA pour apprendre, pas seulement pour produire.

Considère l'IA comme un développeur junior très rapide et très sûr de lui, y compris quand il se trompe. Elle a appris sur des années de code React, dont beaucoup est ancien. Toi, tu restes l'architecte et le relecteur. Tout ce cours sert à ça : comprendre ce qu'elle écrit.

Un bon prompt contient

  1. Le contexte technique : versions de React et des bibliothèques (copie les lignes du package.json).
  2. Les fichiers concernés : le composant, les hooks et contextes qu'il utilise.
  3. L'objectif et les contraintes : « suis le motif existant », « pas de nouvelle dépendance », « garde l'état local ».
  4. La forme de la réponse : un plan d'abord, puis de petites modifications expliquées.

Les signaux d'alerte en relecture

Tu vois…Pourquoi c'est suspect
Un useEffect qui fait juste setX(calcul(...))Valeur dérivée : un rendu de retard et un risque d'incohérence. Calcul direct dans le rendu.
// eslint-disable-next-line react-hooks/exhaustive-depsLe linter a vu une dépendance manquante et on l'a fait taire : closure périmée probable.
push, sort(), obj.x = … sur un étatMutation : l'écran ne se met pas à jour, ou de façon aléatoire.
key={index} ou key={Math.random()}État qui glisse entre les lignes, ou éléments recréés à chaque rendu.
Un fetch dans un effet sans nettoyageRéponses périmées. Et si le projet utilise déjà React Query, l'IA réinvente la roue.
Un composant déclaré dans un autre composantÉtat perdu et focus perdu à chaque rendu.
useMemo et useCallback partoutOptimisation sans mesure ; inutile avec le React Compiler.
Un contexte géant qui contient toutTous les consommateurs se re-rendent à chaque changement.
Composants en classe, ReactDOM.render, create-react-app, defaultProps sur une fonction, forwardRef dans du code neufAPIs anciennes. ReactDOM.render et defaultProps sur les fonctions ont été supprimés en React 19.
Une fonction ou une option que tu ne trouves nulle partAPI inventée. Vérifie sur react.dev ou dans la doc de la bibliothèque.
Un composant de plusieurs centaines de lignes qui charge, calcule et afficheÀ découper : custom hook pour la logique, sous-composants pour l'affichage.

Piège · sécurité

  • Tout le code front est public. Une clé d'API placée dans le code React, y compris dans une variable VITE_…, finit dans le JavaScript téléchargé par le navigateur. Les secrets restent côté backend.
  • dangerouslySetInnerHTML avec du contenu venu d'un utilisateur ouvre la porte aux failles XSS.
  • Une validation côté front améliore l'expérience, mais ne protège rien : ton API doit tout revalider.

Apprendre avec l'IA

  • Explique, puis reformule : demande une explication, puis réexplique avec tes mots et demande à l'IA de corriger ta compréhension.
  • Demande ce qui pourrait casser : « quels cas limites ce code ne gère-t-il pas ? »
  • Fais écrire les tests : une proposition de tests avec Testing Library révèle souvent des comportements que tu n'avais pas imaginés.
  • Avance par petits pas : un plan, une petite modification, tu lances, tu lis le diff, tu demandes « pourquoi ? » sur chaque ligne obscure, tu commites.

L'IA propose useEffect(() => setTotal(items.reduce((s, i) => s + i.price, 0)), [items]). Ta réaction ?

Le total se calcule à partir de items : c'est une valeur dérivée. L'effet ajoute un rendu intermédiaire faux et un état de plus à maintenir. Le signal d'alerte n°1 de la grille.
