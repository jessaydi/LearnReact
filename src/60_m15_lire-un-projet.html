Pratique

Lire un projet inconnu et y ajouter une fonctionnalité

Objectifs

  • Savoir dans quel ordre lire un projet React existant.
  • Suivre une donnée de l'écran jusqu'à l'API, sur un vrai cas.
  • Décrire n'importe quel composant avec cinq questions.
  • Ajouter une fonctionnalité en choisissant le bon endroit pour l'état.

Ce module rassemble tout le cours. Tu arrives sur un projet que tu n'as pas écrit : des centaines de fichiers, des noms que tu ne connais pas. L'objectif n'est pas de tout lire, mais de savoir où regarder.

L'ordre de lecture

  1. package.jsonidentifie la pile technique avant de lire une seule ligne de code.
  2. main.jsxles providers globaux disent quels services sont disponibles partout.
  3. Les routesla carte URL → page : les écrans de l'application.
  4. Une pagesuis une donnée de bout en bout, de l'écran à l'API.

2. Lire les providers de main.jsx

Chaque provider est un contexte (module 10). En lisant cette pile, tu sais ce que n'importe quel composant peut demander : useAuth(), useTheme(), et des requêtes React Query.

Côté backend

Cette pile joue le rôle de la configuration de démarrage d'une API : l'enregistrement des services et des middlewares, dans l'ordre. C'est le premier fichier à lire pour savoir de quoi dispose le reste du code.

3. Lire les routes

C'est la table de routage de l'application : chaque URL pointe vers un composant de page. Pour un bug signalé sur « la page des tâches », tu sais maintenant quel fichier ouvrir en premier.

Suivre une donnée : remonter la piste

Un bug réel, et la façon de le traquer. On part de l'écran et on remonte, fichier par fichier, en se posant toujours la même question : d'où vient cette valeur ?

Démo · remonter la piste d'un bugÉtape 1 / 5

Le bug L'en-tête affiche « 3 tâches restantes » alors qu'une des trois tâches est terminée.

src/components/Header.jsx

Ce qu'on observe. Dans les DevTools, la prop remaining de Header vaut 3. Le composant affiche fidèlement ce qu'il reçoit.

Conclusion. Le bug n'est pas ici : la valeur arrive déjà fausse. Question suivante : qui rend Header ? Les DevTools répondent « rendered by AppLayout ».

src/components/AppLayout.jsx

Ce qu'on observe. AppLayout ne calcule rien : il transmet stats.remaining, qui vient d'un custom hook.

Conclusion. On ouvre useTaskStats, sans s'attarder sur le reste du fichier.

src/hooks/useTaskStats.js

Ce qu'on observe. remaining vaut tasks.length, exactement comme total. Une tâche terminée est comptée comme restante.

Conclusion. C'est probablement le bug. Mais avant de corriger, on vérifie que les données d'entrée sont justes : si l'API renvoyait toutes les tâches à « non terminée », le calcul ne serait pas en cause.

Onglet Réseau · GET /api/tasks

[
  { "id": 1, "title": "Lire",   "done": true },
  { "id": 2, "title": "Coder",  "done": false },
  { "id": 3, "title": "Tester", "done": false }
]

Ce qu'on observe. L'API renvoie bien une tâche terminée, avec le champ done attendu.

Conclusion. Les données sont justes, le contrat aussi : le bug est bien dans le calcul de useTaskStats.

La correction · src/hooks/useTaskStats.js

On vérifie. L'en-tête affiche « 2 tâches restantes ». On cherche ensuite qui d'autre utilise useTaskStats (une recherche dans le projet) : la pastille du menu, par exemple, était fausse elle aussi et se trouve corrigée du même coup.

Ce qu'il faut retenir. On a traversé quatre fichiers sans en lire un seul en entier. À chaque étape, une seule question : d'où vient cette valeur ?

La fiche d'identité d'un composant

Pour comprendre n'importe quel composant, sans tout lire, réponds à cinq questions. C'est aussi un excellent prompt à donner à une IA (module 16).

  1. Ses propsque reçoit-il de son parent ?
  2. Son étatque mémorise-t-il lui-même ?
  3. Ses contextes et hooksque va-t-il chercher ailleurs ?
  4. Ses effetsque fait-il vers l'extérieur ?
  5. Son affichageque montre-t-il, et sous quelles conditions ?

Exercice · remplis la fiche

Voir la solution
  1. Props : taskId (quelle tâche afficher) et onClose (un callback pour fermer le panneau).
  2. État : isEditing, qui dit si le formulaire de modification est ouvert.
  3. Contextes et hooks : useAuth() pour l'utilisateur connecté, useTask(taskId) pour charger la tâche.
  4. Effets : il synchronise le titre de l'onglet avec le titre de la tâche.
  5. Affichage : un indicateur pendant le chargement ; sinon le titre, un bouton « Modifier » seulement si l'utilisateur est propriétaire de la tâche, le formulaire si on est en mode édition, et un bouton « Fermer ».

Ajouter une fonctionnalité, pas à pas

La demande : « ajouter une case pour masquer les tâches terminées ». Voici le composant existant :

On avance en cinq questions, toujours les mêmes :

  1. Qu'est-ce qui existe déjà ? TaskList reçoit les tâches en prop et les affiche toutes. Rien à charger, rien à modifier côté données.
  2. Quelle nouvelle information faut-il mémoriser ? Un booléen : « masquer les terminées ».
  3. Où vit cette information ? Qui en a besoin ? Seulement TaskList. Donc un état local.
  4. Qu'est-ce qui se calcule ? La liste affichée : c'est une valeur dérivée, pas un nouvel état, et pas un effet.
  5. Quels cas limites ? Une liste vide une fois filtrée.

La demande évolue souvent. Si l'en-tête doit aussi connaître ce réglage, l'état remonte chez le parent commun. S'il doit survivre au rechargement de la page, on le persiste avec useLocalStorage (module 11), ou dans l'URL (?hideDone=1) pour qu'un lien partagé conserve le filtre.

Où mettre cet état ?

C'est la question qui revient à chaque fonctionnalité. Réponds pour une donnée précise :

Aide à la décision · où vit cette donnée ?

    Cette donnée vient-elle du serveur (une liste de tâches, un profil, des statistiques) ?

    Doit-elle survivre au rechargement de la page, ou être partageable par un lien ?

    Un seul composant s'en sert-il ?

    Les composants qui s'en servent sont-ils proches (un parent commun à un ou deux niveaux) ?

    La valeur change-t-elle rarement (thème, utilisateur connecté, langue) ?

    Un cache de données serveur

    React Query (ou le chargement du framework). Pas de copie dans un useState : plusieurs copies finissent par diverger.

    L'URL ou le stockage du navigateur

    Dans l'URL (?filter=done) pour un lien partageable ; dans localStorage (useLocalStorage) pour une préférence personnelle.

    Un état local

    useState dans ce composant. Place l'état le plus bas possible.

    Remonter l'état

    Chez le parent commun le plus proche, qui passe la valeur et un callback en props (module 07).

    Un contexte

    Un Provider et un hook useXxx avec garde-fou (module 10).

    Un store, si le projet en a un

    Un état lu partout et souvent modifié : Zustand ou Redux Toolkit, si le projet en utilise déjà un. Sinon, commence par remonter l'état et ne change d'outil qu'en cas de vraie difficulté.

    À retenir · avant de commiter

    • La console est propre : aucune erreur, aucun avertissement de key.
    • Aucun état n'est modifié sur place.
    • Les tableaux de dépendances sont complets et le linter ne signale rien.
    • Aucune valeur dérivable n'est stockée dans un état ni calculée dans un effet.
    • Les cas limites sont gérés : liste vide, chargement, erreur.
    • Tu as suivi les conventions déjà présentes dans le projet.

    En bref

    • Lis un projet dans cet ordre : package.json, main.jsx, les routes, puis une page.
    • Pour un bug, pars de l'écran et remonte : d'où vient cette valeur ? Composant, parent, hook, API.
    • Un composant se résume en cinq questions : props, état, contextes et hooks, effets, affichage.
    • Pour une fonctionnalité : ce qui existe, ce qu'il faut mémoriser, où, ce qui se calcule, les cas limites.

    Exercice · découper et ajouter

    Reprends le TodoApp du module 05. Découpe-le en trois composants frères sous un même parent : Header (affiche le nombre de tâches restantes), AddTaskForm et TaskList. Ajoute un bouton « Tout cocher » dans Header. Où vit l'état ?

    Voir la solution

    Les trois composants ont besoin des tâches : l'état vit chez leur parent commun, qui passe les données et des callbacks.

    Le brouillon draft reste local à AddTaskForm : personne d'autre n'en a besoin. Place l'état le plus bas possible.

    La liste des tâches vient de l'API et trois pages l'affichent. Où la garder ?

    Les données serveur ont des besoins propres : cache partagé, rafraîchissement, invalidation après une modification. C'est exactement le rôle de React Query. Plusieurs copies dans des états locaux finissent par diverger.

    Tu arrives sur un projet inconnu. Quel fichier ouvres-tu en premier pour savoir si le projet utilise React Query ?

    Les dépendances listent les outils du projet. @tanstack/react-query dans package.json te dit de chercher des useQuery, et main.jsx confirmera avec un QueryClientProvider.
