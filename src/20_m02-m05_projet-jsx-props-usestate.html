Environnement

Anatomie d'un projet React

Objectifs

  • Comprendre les outils : Node.js, npm, Vite.
  • Savoir à quoi sert chaque fichier d'un projet neuf, et lesquels tu modifieras.
  • Suivre le démarrage de l'application, de index.html au premier composant.
  • Lire l'organisation d'un vrai projet et savoir où ranger chaque chose.

Créer un projet

Installe Node.js (version LTS) puis tape :

Ouvre l'adresse affichée (souvent http://localhost:5173). Modifie src/App.jsx, enregistre : la page se met à jour toute seule, sans rechargement. C'est le hot module replacement (HMR). Quand tu passeras à TypeScript, le modèle s'appellera react-ts.

Piège

Si un tutoriel te fait taper npx create-react-app, il est obsolète : l'équipe React a déprécié cet outil en février 2025. Pour une application de production, la documentation officielle recommande plutôt un framework (Next.js, React Router en mode framework). Vite seul reste parfait pour apprendre et pour les applications monopage classiques.

Le projet, fichier par fichier

Clique sur un fichier pour voir à quoi il sert, si tu y toucheras, et à quoi il ressemble.

mon-app/ src/

index.html tu y touches rarement

La seule page HTML de l'application. Elle est presque vide : une div avec l'identifiant root, et une balise script qui charge main.jsx. Toute l'interface sera construite par React à l'intérieur de cette div.

Tu y modifieras le titre de l'onglet, la langue ou l'icône. Jamais le contenu de la page : c'est le travail de React.

package.json tu y touches souvent

La carte d'identité du projet, l'équivalent d'un pyproject.toml ou d'un .csproj. Elle liste les bibliothèques utilisées et les commandes disponibles.

  • scripts : les commandes que tu lances avec npm run. npm run dev exécute vite.
  • dependencies : ce dont l'application a besoin pour fonctionner. react fournit les composants et les hooks ; react-dom fait le lien avec le DOM du navigateur. Ce sont deux paquets séparés parce que React sait aussi produire des applications mobiles, avec un autre « traducteur » (React Native).
  • devDependencies : les outils utilisés seulement pendant le développement (Vite, le linter). Ils ne partent pas chez l'utilisateur.
  • ^19.3.0 : « 19.3.0 ou toute version compatible plus récente, sans passer à 20 ».

Tu n'édites pas les versions à la main : npm install nom-du-paquet ajoute la ligne pour toi.

package-lock.json tu n'y touches jamais

Généré automatiquement par npm install. Il note la version exacte de chaque paquet installé, y compris les dépendances de tes dépendances, pour que tous les membres de l'équipe et le serveur de build installent exactement la même chose.

C'est l'équivalent d'un poetry.lock ou d'un packages.lock.json. On le commite dans Git, mais on ne l'édite jamais à la main. Il fait souvent plusieurs milliers de lignes : c'est normal.

vite.config.js tu y touches rarement

La configuration de Vite. Le plugin react() lui apprend à comprendre le JSX. Un ajout très utile pour un dev backend : le proxy, qui redirige pendant le développement les appels /api vers ton serveur local.

Avec ce proxy, ton front (port 5173) et ton API (port 8000) se comportent comme s'ils étaient sur le même serveur : pas de configuration CORS pendant le développement.

eslint.config.js tu y touches rarement

La configuration d'ESLint, l'outil qui analyse ton code et signale les erreurs probables, comme ruff ou les analyseurs Roslyn. Le projet inclut les règles react-hooks, qui vérifient les règles des hooks (module 09) et les dépendances des effets (module 08).

Installe l'extension ESLint de ton éditeur : les avertissements apparaissent soulignés pendant que tu tapes. Ils t'éviteront beaucoup de bugs React.

.gitignore tu y touches rarement

La liste de ce que Git doit ignorer. On y trouve notamment node_modules (trop gros, se réinstalle avec npm install) et dist (se régénère avec npm run build). Si tu crées un fichier .env.local pour des réglages locaux, il doit y figurer aussi.

node_modules/ tu n'y touches jamais

Le dossier où npm install télécharge toutes les bibliothèques, comme un environnement virtuel Python. Il est énorme (des centaines de mégaoctets n'ont rien d'anormal) et ne se commite pas.

Si le projet se comporte bizarrement après un changement de branche, le remède classique : supprimer node_modules et relancer npm install.

public/ tu y touches rarement

Les fichiers servis tels quels, sans transformation, à la racine du site : public/favicon.svg sera accessible à l'adresse /favicon.svg. On y met le favicon, un robots.txt, des fichiers qu'on référence par leur URL fixe.

Pour les images utilisées dans tes composants, préfère src/assets/ (voir ce dossier).

src/main.jsx tu y touches rarement

Le point d'entrée du JavaScript, l'équivalent de main.py ou de Program.cs. Il ne fait qu'une chose : brancher React sur la div#root de index.html et y afficher le composant App.

Dans un vrai projet, c'est aussi là qu'on enveloppe App dans les « providers » globaux (authentification, thème, cache de données). On le détaille juste en dessous.

src/App.jsx tu y touches souvent

Le composant racine : le premier de l'arbre, celui qui contient tous les autres. C'est là que tu commences à écrire ton application. Le modèle Vite y met une petite démo avec un compteur, que tu peux effacer.

App.css, index.css tu y touches souvent

Des feuilles de style ordinaires. index.css contient les styles globaux (police, couleurs de fond) et est importé dans main.jsx ; App.css contient les styles de App.

Particularité : on importe un fichier CSS depuis le JavaScript (import "./App.css"). Vite se charge de l'injecter dans la page. Dans les vrais projets, tu verras aussi Tailwind (des classes utilitaires) ou des fichiers *.module.css (styles limités à un composant).

src/assets/ tu y touches souvent

Les images et fichiers utilisés par ton code. On les importe comme un module, et Vite fournit leur URL finale (optimisée, avec un nom unique pour le cache).

Différence avec public/ : un fichier de assets/ est vérifié et optimisé au build (un import cassé provoque une erreur) ; un fichier de public/ est copié sans contrôle.

dist/ généré, jamais modifié

Créé par npm run build. Il contient la version finale : un index.html, et quelques fichiers JavaScript et CSS compressés. Ton JSX a disparu, traduit en JavaScript standard.

C'est ce dossier qu'on déploie : sur nginx, sur un CDN, ou dans le dossier de fichiers statiques de ton application ASP.NET ou FastAPI. Il ne contient que des fichiers statiques : pas besoin de Node.js en production.

Comment l'application démarre

1 · index.htmlle navigateur charge une page quasi vide avec une div #root
→
2 · main.jsxcrée la racine React sur #root
→
3 · <App />React appelle App, qui appelle ses enfants
→
4 · DOMReact crée les éléments, l'écran s'affiche

Relisons main.jsx ligne par ligne :

  • createRoot(document.getElementById("root")) : « React, prends le contrôle de cette div ». Tout ce qui est à l'intérieur t'appartient désormais.
  • .render(<App />) : « affiches-y le composant App ». React appelle la fonction App, puis les composants qu'elle utilise, et ainsi de suite.
  • <StrictMode> : un détecteur de bugs, actif en développement seulement. Il appelle certaines fonctions deux fois pour révéler les erreurs (module 07). Il n'affiche rien.

À partir de là, React ne recharge plus jamais la page. Il met à jour des morceaux de l'écran quand les données changent.

Côté backend

Dans une application monopage (SPA), le serveur envoie une seule page HTML et un paquet de JavaScript. Ensuite, tout se passe dans le navigateur, qui appelle ton API en JSON. Les URL comme /tasks ou /settings sont gérées côté client par une bibliothèque de routage (React Router, par exemple) : changer de page ne fait aucune requête HTML au serveur.

Dans un vrai projet

Le projet neuf ne contient qu'un composant. Une vraie application en contient des dizaines, rangés par rôle. React n'impose aucune organisation, mais tu retrouveras presque toujours ces dossiers. Clique sur chacun.

src/

main.jsx · le démarrage et les services globaux

Comme dans le projet neuf, mais App est enveloppée dans des providers : des composants qui rendent un service disponible à toute l'application (utilisateur connecté, thème, cache des données serveur).

En lisant ce fichier, tu sais ce que n'importe quel composant pourra demander. On y revient au module 15.

router.jsx · quelle page pour quelle URL

La table des routes : chaque adresse pointe vers un composant de page. C'est la carte de l'application.

pages/ · un composant par écran

Une page correspond à une URL. Son travail : assembler. Elle récupère les données (via un hook) et les donne à des composants d'affichage. Elle contient peu de HTML elle-même.

components/ · les briques d'interface du métier

Des composants réutilisables, liés au domaine de l'application : TaskItem, TaskList, UserMenu. Ils reçoivent des données en props et signalent les actions par des callbacks. En règle générale, ils n'appellent pas l'API eux-mêmes : ça les rend faciles à réutiliser et à tester.

components/ui/ · les briques génériques

Les composants qui ne connaissent rien au métier : Button, Modal, Spinner, Input. Ils pourraient servir dans n'importe quelle application. Souvent, ils viennent d'une bibliothèque de composants (shadcn/ui, MUI…) ou d'un « design system » interne.

hooks/ · la logique réutilisable

Les custom hooks (module 11) : des fonctions useXxx qui regroupent de la logique avec état. Charger les tâches, gérer un formulaire, mémoriser une préférence. Une page ou un composant les appelle pour obtenir des données et des actions, sans connaître les détails.

Version volontairement simple : on verra les pièges de ce code au module 08, et React Query le remplacera plus tard.

context/ · les valeurs partagées

Les contextes (module 10) : des valeurs que beaucoup de composants éloignés doivent lire, comme l'utilisateur connecté ou le thème. Chaque fichier exporte en général un Provider (placé dans main.jsx) et un hook pour lire la valeur.

api/ (ou services/) · parler au backend

Les fonctions qui appellent ton API. Elles ne contiennent aucun React : juste du fetch, des URL et la gestion des erreurs HTTP. Si l'URL d'un endpoint change, c'est le seul endroit à modifier.

lib/ (ou utils/) · les fonctions pures

Des fonctions utilitaires sans React ni réseau : formater une date, calculer un total, valider un e-mail. Elles prennent des valeurs et renvoient des valeurs, ce qui les rend triviales à tester.

*.test.jsx · les tests

Souvent rangés à côté du fichier testé (TaskItem.jsx et TaskItem.test.jsx). Avec Vitest et Testing Library, on affiche un composant, on simule un clic, et on vérifie ce que voit l'utilisateur.

Qui appelle qui ?

Ces dossiers forment des couches. Les appels vont toujours dans le même sens, du haut vers le bas :

Côté backend

C'est l'architecture en couches que tu pratiques déjà. Les pages jouent le rôle des contrôleurs (le point d'entrée d'une URL), les hooks celui des services (la logique), api/ celui des clients HTTP ou des repositories (l'accès aux données), et les components celui des vues. Même règle d'or : les dépendances vont dans un seul sens.

Certaines équipes rangent plutôt par fonctionnalité : un dossier features/tasks/ qui regroupe les composants, hooks et appels API des tâches. Les rôles restent les mêmes, seul le rangement change.

En bref

  • Node.js fait tourner les outils, npm installe les bibliothèques, Vite traduit le JSX et sert l'application.
  • Tu travailles presque uniquement dans src/ ; main.jsx branche React sur la page, App.jsx est la racine de l'arbre.
  • Dans un vrai projet : pages (assemblent), components (affichent), hooks (logique), context (partagé), api (backend), lib (fonctions pures).

Pratique

Crée le projet mon-app, lance-le, puis remplace tout le contenu de src/App.jsx par le composant ci-dessous. Enregistre et regarde la page se mettre à jour sans rechargement. Supprime ensuite App.css et la ligne qui l'importe : observe l'erreur affichée par Vite, puis annule. Ce projet te servira de bac à sable pour tout le cours.

À quel endroit React est-il « branché » sur la page HTML ?

main.jsx est le point d'entrée : il crée la racine React sur la div #root de index.html et y affiche App.

Tu dois écrire la fonction qui envoie POST /api/tasks. Dans quel dossier la ranges-tu ?

Les appels HTTP vivent dans api/, sans React. Un hook ou une page les utilise, et les composants d'affichage restent simples. lib/ est réservé aux fonctions pures, sans réseau.

03

Les briques

Composants et JSX

Objectifs

  • Écrire un composant et l'utiliser.
  • Comprendre ce que devient le JSX, pour que ses règles deviennent logiques.
  • Connaître les dix règles de JSX, avec les messages d'erreur associés.
  • Découper un écran en composants.

Un composant, c'est une fonction

Trois choses font d'une fonction un composant :

  1. c'est une fonction JavaScript ordinaire ;
  2. son nom commence par une majuscule (Greeting, pas greeting) ;
  3. elle renvoie du JSX, c'est-à-dire la description de ce qu'il faut afficher (ou null pour ne rien afficher).

On l'utilise ensuite comme une balise : <Greeting />. Quand React rencontre cette balise, il appelle la fonction Greeting() et regarde ce qu'elle renvoie. Ici, App l'utilise deux fois : React appelle donc Greeting deux fois, et le titre apparaît deux fois.

Qu'est-ce que JSX, exactement ?

JSX ressemble à du HTML, mais ce n'en est pas. Avant d'arriver dans le navigateur, Vite le traduit en JavaScript : chaque balise devient un appel de fonction. Cet appel produit un petit objet qui décrit l'élément voulu (React l'appelle un « élément »). Enfin, React utilise ces descriptions pour créer ou modifier le DOM.

Choisis un exemple et suis-le à travers les quatre étapes :

Les attributs deviennent les clés d'un objet JavaScript. C'est pour ça qu'on écrit className : class est un mot réservé de JavaScript.

Les balises enfants deviennent des appels imbriqués, rangés dans children. Le JSX décrit un arbre ; l'objet produit est un arbre ; le DOM final est un arbre.

Ce qui est entre accolades est copié tel quel dans l'appel de fonction : c'est du JavaScript évalué. Voilà pourquoi on ne peut y mettre qu'une expression (règle 3).

Avec une minuscule (<h1>), Vite écrit la chaîne "h1" : une balise HTML. Avec une majuscule (<Greeting>), il écrit la variable Greeting : ta fonction. C'est la règle 7. Note aussi que le composant n'apparaît pas dans le DOM : seul ce qu'il renvoie y arrive.

Les règles de JSX, une par une

Presque toutes les règles découlent de ce que tu viens de voir : le JSX devient des appels de fonctions et des objets JavaScript. Pour chaque règle : ce qu'elle dit, pourquoi elle existe, un exemple faux puis juste, et le message que tu verras si tu l'oublies.

Règle 1 Un composant renvoie un seul élément racine

Pourquoi ? Une fonction ne renvoie qu'une seule valeur. Deux balises côte à côte, ce seraient deux appels jsx(...) à renvoyer en même temps : impossible. Il faut les regrouper dans un parent.

<>…</> s'appelle un Fragment : il regroupe sans rien ajouter dans le DOM. On aurait pu utiliser une div, mais une balise inutile peut casser une mise en page (une grille, un tableau, une liste ul/li).

Message : Adjacent JSX elements must be wrapped in an enclosing tag

Règle 2 Toutes les balises se ferment

Pourquoi ? Le traducteur doit savoir exactement où se termine chaque appel. Le HTML tolère <br> ou <img> sans fermeture ; JSX non. Une balise sans contenu se ferme elle-même avec />.

Message : Expected corresponding JSX closing tag for <img>

Règle 3 Les accolades ouvrent une fenêtre sur JavaScript

Dans du JSX, tout est du texte fixe, sauf ce qui est entre accolades { } : là, c'est du JavaScript, évalué au moment du rendu. Les accolades peuvent apparaître à deux endroits : dans le contenu d'une balise, et comme valeur d'un attribut.

Pourquoi seulement des expressions ? Le contenu des accolades atterrit tel quel comme argument d'un appel de fonction (onglet « Une expression » ci-dessus). On peut écrire f(a ? b : c), mais pas f(if (a) b). Une expression produit une valeur (a + b, x ? y : z, list.map(...)) ; une instruction fait quelque chose (if, for, const) et ne passe pas.

Ce que React affiche selon le type de la valeur placée entre accolades :

ValeurExempleCe qui s'affiche

nombre{3}, {0}le nombre, y compris 0
booléen{true}, {false}rien
null, undefined{null}rien
tableau{["a", "b"]}chaque élément, à la suite : ab

Messages : Unexpected token (instruction dans les accolades) ; Objects are not valid as a React child (objet affiché directement : écris {user.name}).

Règle 4 Un attribut prend des guillemets OU des accolades, jamais les deux

  • Guillemets pour une chaîne fixe : alt="Photo de profil".
  • Accolades pour tout le reste : une variable, un nombre, un booléen, une fonction, un objet.

Règle 5 Les noms d'attributs s'écrivent en camelCase

Pourquoi ? Les attributs deviennent les clés d'un objet JavaScript, et React utilise les noms des propriétés du DOM, qui sont en camelCase (tabIndex, et non tabindex).

HTMLJSXRaison

Message (dans la console) : Invalid DOM property `class`. Did you mean `className`?

Règle 6 style reçoit un objet, pas une chaîne

Les propriétés CSS passent en camelCase (font-size devient fontSize) et un nombre seul est compris comme des pixels. En pratique, on préfère des classes CSS et on garde style pour des valeurs calculées (une largeur en pourcentage, une couleur choisie par l'utilisateur).

Message : The `style` prop expects a mapping from style properties to values, not a string

Règle 7 Majuscule pour un composant, minuscule pour une balise HTML

Pourquoi ? Le traducteur se fie à la première lettre. <button> devient la chaîne "button" (une balise HTML) ; <Button> devient la variable Button (ta fonction, qui doit donc être importée).

Messages : The tag <taskBadge> is unrecognized in this browser ; TaskBadge is not defined (import oublié).

Règle 8 Un return sur plusieurs lignes s'entoure de parenthèses

Pourquoi ? JavaScript ajoute automatiquement un point-virgule après un return suivi d'un retour à la ligne. Le composant renvoie alors undefined et le JSX en dessous n'est jamais atteint.

Règle 9 Les commentaires s'écrivent entre accolades

Règle 10 Le texte est protégé automatiquement

Tout ce que tu affiches entre accolades est traité comme du texte, jamais comme du HTML. Si un utilisateur malveillant saisit un titre de tâche contenant une balise <script>, elle s'affichera telle quelle, sans être exécutée.

Côté backend

C'est le principe d'une requête SQL paramétrée : la donnée ne peut jamais devenir du code. Pour insérer du vrai HTML, il faut passer par dangerouslySetInnerHTML, dont le nom est un avertissement : à réserver à du contenu nettoyé et de confiance.

Piège

  • Composant déclaré dans un autre composant : il est recréé à chaque affichage, ce qui efface son état et fait perdre le focus aux champs de saisie. Déclare toujours tes composants au premier niveau du fichier.

En bref

  • Un composant est une fonction à majuscule qui renvoie du JSX ; React l'appelle quand il rencontre sa balise.
  • Le JSX devient des appels de fonctions, qui produisent des objets décrivant l'écran ; React s'en sert pour modifier le DOM.
  • D'où les règles : une seule racine, tout se ferme, accolades pour les expressions, camelCase, style en objet.

Exercice 2 · ton premier composant

Crée un composant ProfileCard qui affiche un nom, un rôle, l'initiale du nom dans une pastille, et un badge « Disponible » seulement si la personne l'est. Pour l'instant, les données viennent d'une variable dans le composant.

Voir la solution

{user.available && …} affiche le badge seulement si la condition est vraie. On détaillera ce motif au module 06.

Pourquoi écrit-on className au lieu de class en JSX ?

JSX est traduit en JavaScript : className="title" devient { className: "title" }. React reprend le nom de la propriété du DOM, className.

Que s'affiche-t-il avec <img src="{user.avatarUrl}" /> ?

Entre guillemets, tout est du texte fixe. Pour évaluer du JavaScript, il faut des accolades seules : src={user.avatarUrl}.

04

Les briques

Props : passer des données à un composant

Objectifs

  • Passer et recevoir des props, avec des valeurs par défaut.
  • Utiliser children pour composer des cadres réutilisables.
  • Comprendre le flux à sens unique : les données descendent, les événements remontent.

Les props sont les paramètres d'un composant

Un composant sans paramètres affiche toujours la même chose. Les props (pour properties) permettent de lui passer des informations, exactement comme on passe des arguments à une fonction.

Ce qu'il faut comprendre : quand tu écris <Avatar name="Ada Lovelace" size={64} online />, React rassemble tous les attributs dans un objet et appelle ta fonction avec : Avatar({ name: "Ada Lovelace", size: 64, online: true }). Les props, c'est ce seul objet. Change les props ci-dessous et observe les deux lignes de code :

Démo · les props d'Avatar
A

Ce que tu écris

<Avatar name="Ada Lovelace" size={64} online />

Ce que React fait

Avatar({ name: "Ada Lovelace", size: 64, online: true })
  • Une chaîne fixe s'écrit entre guillemets : name="Ada".
  • Tout le reste entre accolades : nombres, booléens, objets, tableaux, fonctions, et même du JSX.
  • Une prop écrite seule vaut true : online équivaut à online={true}. Absente, elle prend sa valeur par défaut (ici false).

children : le contenu placé entre les balises

Une prop est spéciale : children. Elle contient tout ce que l'appelant place entre la balise ouvrante et la balise fermante du composant.

Les props sont en lecture seule

Un composant ne modifie jamais ses props. Elles appartiennent au parent qui les a fournies.

Les données descendent, les événements remontent

Le spread de props

Tu croiseras souvent ce motif dans les composants génériques. Pratique, mais il rend moins visible ce qui passe d'un composant à l'autre.

En bref

  • Les props sont les paramètres d'un composant : React les rassemble dans un objet et appelle ta fonction avec.
  • children contient ce qui est placé entre les balises : c'est ce qui permet de faire des cadres réutilisables.
  • Les données descendent (props), les événements remontent (callbacks). Quand l'écran est faux, on remonte vers le composant qui possède la donnée.

Voir la solution

Un composant enfant veut changer une donnée qu'il a reçue en prop. Que fait-il ?

La donnée appartient au parent. L'enfant appuie sur la « sonnette » (onToggle), le parent met à jour son état, et la nouvelle valeur redescend en prop. Copier la prop dans un état local crée deux versions qui finissent par se contredire.

Pourquoi une variable ordinaire ne suffit pas

Deux problèmes :

  1. Rien ne déclenche un nouvel affichage. React ne surveille pas tes variables. Il ne refait le rendu que si on le lui demande.
  2. Même s'il refaisait le rendu, la fonction serait rappelée depuis le début, et let count = 0 remettrait tout à zéro.

Manipule la démo : clique plusieurs fois à gauche, puis provoque un re-rendu.

Nombre de rendus de Counter : 1

La solution : useState

useState(0) renvoie un tableau de deux éléments, qu'on déstructure : la valeur actuelle et une fonction pour la changer (le « setter »). Ce que fait le setter, dans l'ordre :

  1. setCount(1)enregistre la nouvelle valeur et demande un nouveau rendu. count ne change pas tout de suite.
  2. React rappelle Counter()la fonction s'exécute à nouveau, du début à la fin.
  3. useState renvoie 1React a gardé la valeur de côté ; la valeur initiale 0 est ignorée.
  4. React met le DOM à jouril compare et ne modifie que le texte « Clics : 1 ».

Analogie

Ton composant est un employé qui perd la mémoire à chaque appel : il recommence son travail de zéro à chaque rendu. useState lui donne un casier à son nom, géré par React. À chaque rendu, il ouvre son casier et y trouve la dernière valeur. Et changer le contenu du casier passe par un guichet (le setter), qui prévient React de refaire le travail.

L'état est une photo prise au moment du rendu

Pendant un rendu, count est une constante : une photo de la valeur à cet instant. Le setter ne modifie pas la photo ; il prépare la valeur du rendu suivant. Règle simple : si la nouvelle valeur dépend de l'ancienne, passe une fonction au setter (c => c + 1). React lui donnera toujours la valeur la plus récente.

React regroupe aussi tous les appels de setters d'un même événement en un seul nouveau rendu (le batching). Trois setX dans un clic, c'est un seul rendu.

Objets et tableaux : pourquoi il faut créer une copie

C'est la partie qui surprend le plus. Prenons-la en cinq étapes, en nous appuyant sur la notion de référence vue au module 01.

Étape 1 · Une variable ne contient pas l'objet, elle pointe vers lui

Quand l'état contient un objet, la variable user ne contient pas l'objet lui-même mais son adresse en mémoire. Comme un papier sur lequel est notée l'adresse d'une maison.

user → objet n°1
objet n°1{ name: "Ada", email: "ada@mail.com" }

Étape 2 · Comment React décide de refaire l'affichage

Quand tu appelles setUser(x), React compare x à la valeur actuelle avec Object.is, l'équivalent de ===. Pour des objets, cette comparaison regarde l'adresse, pas le contenu :

  • même adresse → « rien n'a changé » → React ne fait rien ;
  • adresse différente → « quelque chose a changé » → React refait le rendu.

Pourquoi ne pas comparer le contenu ? Parce que fouiller l'intérieur de gros objets à chaque mise à jour serait lent. Comparer deux adresses est instantané.

Étape 3 · Modifier sur place ne change pas l'adresse

React est un facteur qui ne vérifie que l'adresse sur l'enveloppe. Si tu repeins l'intérieur de la maison mais que tu lui redonnes la même adresse, il considère qu'il n'y a rien de nouveau à livrer. Pour qu'il passe, il faut une nouvelle maison, donc une nouvelle adresse.

Étape 4 · Le spread : une photocopie avec une correction

Lis cette ligne en trois temps :

  1. { } : construis un nouvel objet, donc une nouvelle adresse.
  2. ...user : recopie dedans toutes les propriétés de user (name: "Ada", email: …).
  3. name: "Grace" : puis remplace name. La dernière valeur écrite gagne.

Résultat : { name: "Grace", email: "ada@mail.com" }, à une nouvelle adresse. L'ordre compte : { name: "Grace", ...user } recopierait user par-dessus et name redeviendrait « Ada ».

Étape 5 · Les objets imbriqués : copier chaque niveau modifié

Le spread ne copie qu'un seul niveau. Si user contient un objet address, la copie recopie l'adresse de cet objet intérieur, pas l'objet lui-même : les deux versions partagent la même address.

user → objet n°1 copie → objet n°2
objet n°1{ name: "Ada", address: → n°3 }
objet n°2{ name: "Ada", address: → n°3 }
objet n°3 (partagé !){ city: "Paris" }

Règle pratique : sur le chemin qui mène à la valeur modifiée, chaque objet doit être recopié. Le reste peut être partagé sans danger, puisqu'on n'y touche pas.

Les tableaux : le même principe

Un tableau est un objet : même règle. Les méthodes qui modifient le tableau (push, splice, sort, affectation arr[0] = …) gardent la même adresse ; React ne voit rien. Les méthodes qui créent un nouveau tableau ([...], filter, map) changent l'adresse. Essaie les deux familles :
