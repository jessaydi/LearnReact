Hooks · la boîte à outils

Les règles des hooks et les autres hooks que tu croiseras

Objectifs

  • Connaître les deux règles des hooks et voir concrètement pourquoi elles existent.
  • Choisir entre une variable, une ref et un état.
  • Comprendre ce que font memo, useMemo et useCallback, et quand ils servent vraiment.
  • Lire et écrire un useReducer.

Les deux règles des hooks

  1. On appelle les hooks au premier niveau du composant : jamais dans un if, une boucle, une fonction imbriquée, ni après un return anticipé.
  2. On les appelle uniquement depuis un composant React ou depuis un custom hook (module 11).

Ces règles paraissent arbitraires tant qu'on ne sait pas comment React retrouve tes états d'un rendu à l'autre. Regardons-le.

Pourquoi : React range les hooks par ordre d'appel

Quand tu écris const [age, setAge] = useState(36), React ne voit pas le nom age. Il voit seulement « le 2e hook appelé par ce composant ». Il range les valeurs dans des cases numérotées, dans l'ordre d'appel, et au rendu suivant il les redonne dans le même ordre.

Analogie

Un vestiaire où l'on rend les manteaux dans l'ordre des tickets, sans regarder les visages. Tant que tout le monde passe dans le même ordre, chacun récupère son manteau. Si quelqu'un passe son tour, toutes les personnes suivantes repartent avec le manteau de leur voisin.

Avec le hook dans un if, perms récupère l'âge et age ne trouve rien : React lève l'erreur Rendered more hooks than during the previous render. La solution : appeler tous les hooks à chaque rendu, et mettre la condition dans l'affichage, pas autour du hook.

Une seule exception : use (module 12) peut s'appeler dans une condition. Le plugin ESLint react-hooks, installé dans les projets Vite, vérifie ces règles à ta place.

La mémoïsation : memo, useMemo et useCallback

Mémoïser, c'est garder en mémoire le résultat d'un calcul pour ne pas le refaire si les entrées n'ont pas changé, comme un @lru_cache en Python. React propose trois outils, qui répondent à un même problème.

Le problème

On l'a vu au module 07 : quand un parent se re-rend, tous ses enfants se re-rendent. D'habitude, c'est sans importance. Mais si un enfant est lent à rendre (une liste de 5 000 lignes, un graphique), le re-rendre pour rien devient visible.

memo : sauter le rendu d'un composant

Avant de re-rendre un composant enveloppé dans memo, React compare chacune de ses props avec la précédente (avec Object.is). Si toutes sont identiques, il réutilise le résultat précédent.

À retenir · le React Compiler

Depuis octobre 2025, le React Compiler (version 1.0 stable) ajoute automatiquement cette mémoïsation au moment du build. Pour du nouveau code, l'équipe React recommande de s'appuyer sur lui et de garder useMemo et useCallback comme échappatoires ponctuelles. Dans les projets existants et dans le code généré par une IA, tu en verras partout : sache les lire, n'en ajoute pas « au cas où ».

useReducer : centraliser les mises à jour

Dans TaskFlow, les tâches sont modifiées à plusieurs endroits : ajout, case à cocher, suppression, renommage. Chaque gestionnaire contient sa propre logique de mise à jour, éparpillée dans le composant. Quand cette logique grossit, on la regroupe dans une seule fonction pure, le reducer.

  1. Un clicl'utilisateur coche une tâche
  2. dispatch(action)le gestionnaire décrit ce qui s'est passé : { type: "toggled", id: 2 }
  3. reducer(état, action)calcule le nouvel état à partir de l'ancien
  4. Nouvel étatReact le range et refait le rendu

Le gestionnaire ne dit plus comment modifier les données, seulement ce qui s'est passé. C'est le reducer qui décide. Envoie des actions et observe quelle branche s'exécute :

Démo · le reducer en action
function tasksReducer(tasks, action) {
  switch (action.type) {
    case "added":
      return [...tasks, { id: action.id, title: action.title, done: false }];
    case "toggled":
      return tasks.map(t => (t.id === action.id ? { ...t, done: !t.done } : t));
    case "deleted":
      return tasks.filter(t => t.id !== action.id);
    default:
      throw new Error(`Action inconnue : ${action.type}`);
  }
}

    Côté backend

    Un reducer, c'est un gestionnaire de commandes pur, ou la méthode apply(state, event) d'un agrégat en event sourcing : (état, action) → nouvel état. Il se teste unitairement sans React : on lui donne un état et une action, on vérifie le résultat. C'est aussi le principe de Redux, que tu croiseras dans certains projets.

    Quand passer de useState à useReducer ? Quand plusieurs gestionnaires modifient le même état de façons différentes, ou quand la logique de mise à jour mérite d'être testée seule. Pour un booléen ou un champ texte, useState reste plus simple.

    Quel hook pour quel besoin ?

    Je veux…J'utilise
    une valeur qui, en changeant, met l'écran à jouruseState (ou useReducer si la logique est riche)
    une valeur calculable à partir d'autresrien : une simple variable dans le rendu
    me synchroniser avec un système extérieuruseEffect avec nettoyage
    accéder à un élément du DOM, ou garder une valeur sans re-renduuseRef
    partager une valeur avec tout un sous-arbreuseContext (module 10)
    réutiliser une logique avec état dans plusieurs composantsun custom hook (module 11)

    En bref

    • React retrouve tes hooks par leur ordre d'appel : jamais de hook dans une condition, une boucle ou après un return.
    • let repart de zéro à chaque rendu, une ref survit sans déclencher de rendu, un état survit et déclenche un rendu.
    • memo saute un rendu si les props sont identiques ; useCallback et useMemo gardent la même fonction ou le même résultat. Le React Compiler fait ce travail pour toi.
    • useReducer centralise les mises à jour : les gestionnaires envoient des actions, le reducer calcule le nouvel état.

    Exercice · passer à useReducer

    Ce compteur a trois boutons qui modifient le même état. Réécris-le avec useReducer et trois actions : incremented, decremented, reset. Le compteur ne doit jamais descendre sous 0.

    Voir la solution

    Pourquoi ne peut-on pas appeler useState dans un if ?

    React associe les valeurs aux hooks par position : 1er appel, 2e appel… Un hook conditionnel décale tous les suivants d'un rendu à l'autre, et chaque hook récupère la valeur d'un autre.

    Tu veux mémoriser l'identifiant d'un minuteur pour pouvoir l'arrêter plus tard. Il ne s'affiche nulle part. Que choisis-tu ?

    Un let serait perdu au rendu suivant, et un état provoquerait des rendus inutiles. Une ref garde la valeur entre les rendus sans en déclencher.
