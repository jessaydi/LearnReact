Méthode

L'IA comme copilote, sans perdre le contrôle

Objectifs

  • Donner à l'IA le contexte qui produit du bon code React.
  • Travailler par petits pas vérifiables plutôt que par grosses générations.
  • Relire le code généré avec une grille de signaux d'alerte, et t'y entraîner.
  • Utiliser l'IA pour apprendre, pas seulement pour produire.

Considère l'IA comme un développeur junior très rapide et très sûr de lui, y compris quand il se trompe. Elle a appris sur des années de code React, dont une bonne partie est ancienne : composants en classe, create-react-app, effets partout. Toi, tu restes l'architecte et le relecteur. Tout ce cours sert à ça : comprendre ce qu'elle écrit.

Ce que doit contenir un bon prompt

  1. Le contexte techniqueles versions de React et des bibliothèques : copie les lignes utiles du package.json.
  2. Les fichiers concernésle composant, et les hooks et contextes qu'il utilise.
  3. L'objectif et les contraintes« suis le motif existant », « pas de nouvelle dépendance », « garde l'état local ».
  4. La forme de la réponseun plan d'abord, puis de petites modifications expliquées.

Sans contexte, l'IA devine : elle choisit une bibliothèque que tu n'utilises pas, ou une API d'une ancienne version de React. Avec le contexte, elle suit les conventions de ton projet.

Remarque le point commun : on demande d'abord une explication ou un plan, puis du code. Le plan se relit en trente secondes ; trois cents lignes de code, non.

Travailler par petits pas

  1. Planquel composant possède l'état, quels fichiers changent
  2. Une petite modificationun fichier ou une fonction à la fois
  3. Lancerla page fonctionne, la console est propre
  4. Lire le diffchaque ligne, avec la grille ci-dessous
  5. Demander « pourquoi ? »sur toute ligne que tu ne saurais pas réexpliquer
  6. Commiterpuis le pas suivant

Si une modification casse quelque chose, tu sais exactement laquelle, et tu peux revenir en arrière sans perdre le reste. Une génération de dix fichiers d'un coup ne permet ni l'un ni l'autre.

Voir la version corrigée

La version corrigée est plus courte, sans effet, et toujours juste dès le premier rendu. Un signe fréquent : quand du code React se simplifie en le corrigeant, c'est qu'on se rapproche du bon modèle.

Piège · sécurité

  • Tout le code front est public. Une clé d'API placée dans le code React, y compris dans une variable VITE_…, finit dans le JavaScript téléchargé par le navigateur. Les secrets restent côté backend.
  • dangerouslySetInnerHTML avec du contenu venu d'un utilisateur ouvre la porte aux failles XSS.
  • Une validation côté front améliore l'expérience, mais ne protège rien : ton API doit tout revalider.

Apprendre avec l'IA

  • Explique, puis reformule : demande une explication, réexplique avec tes mots, et demande à l'IA de corriger ta compréhension.
  • Demande ce qui pourrait casser : « quels cas limites ce code ne gère-t-il pas ? »
  • Fais écrire les tests : une proposition de tests avec Testing Library révèle souvent des comportements auxquels tu n'avais pas pensé.
  • Demande la fiche d'identité d'un composant (module 15) : props, état, contextes et hooks, effets, affichage.
  • Vérifie les affirmations sur les versions et les API dans la documentation officielle : c'est là que l'IA se trompe le plus souvent.

En bref

  • Un bon prompt donne les versions, les fichiers, les contraintes, et demande un plan avant le code.
  • Avance par petits pas : une modification, on lance, on lit le diff, on demande pourquoi, on commite.
  • Relis avec la grille : effets inutiles, dépendances muselées, mutations, keys instables, APIs anciennes ou inventées, failles de sécurité.

L'IA propose useEffect(() => setTotal(items.reduce((s, i) => s + i.price, 0)), [items]). Ta réaction ?

Le total se calcule à partir de items : c'est une valeur dérivée. L'effet ajoute un rendu intermédiaire faux et un état de plus à maintenir. C'est le signal d'alerte n°1 de la grille.
