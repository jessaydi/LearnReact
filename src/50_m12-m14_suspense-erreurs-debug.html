Chargement

Suspense et lazy : déclarer les états de chargement

Objectifs

  • Comprendre ce que veut dire « un composant suspend ».
  • Découper le code avec lazy pour charger une page à la demande.
  • Savoir ce qui déclenche Suspense, et ce qui ne le déclenche pas.

L'idée

Jusqu'ici, chaque composant gérait son propre isLoading. Suspense inverse la logique : un composant qui n'est pas prêt (son code ou ses données sont en cours de chargement) suspend, et le <Suspense> le plus proche au-dessus affiche un contenu de remplacement à sa place.

Analogie

Au théâtre, le rideau reste baissé tant que le décor n'est pas en place. Les comédiens ne viennent pas un par un annoncer « je ne suis pas prêt ». <Suspense> est le rideau, fallback est ce qu'on projette dessus en attendant.

Côté backend

C'est un await déclaratif. Le composant « attend » quelque chose, et c'est l'endroit où tu as placé <Suspense> qui décide de ce qu'on voit pendant l'attente.

Ce qui peut faire suspendre un composant

  1. Un composant chargé avec lazy, dont le code n'est pas encore téléchargé.
  2. Des données lues via une source compatible Suspense : un framework comme Next.js, useSuspenseQuery de React Query, ou use(promesse) avec une promesse mise en cache.

Piège

Suspense ne détecte pas les données chargées dans un useEffect. Avec le motif du module 08, c'est ton propre isLoading qui gère l'affichage, et le fallback ne s'affiche jamais.

lazy : charger le code à la demande

Sans lazy, tout le code de l'application part dans un seul gros fichier JavaScript, téléchargé dès la première visite. Avec lazy, Vite découpe le code : celui du tableau de bord n'est téléchargé que si un administrateur l'affiche. On l'utilise surtout pour les pages et les composants lourds (éditeurs, graphiques).

C'est l'équivalent d'un Lazy<T> en C#, ou d'un import placé à l'intérieur d'une fonction en Python.

use : lire une promesse

Le composant ne contient plus que le cas nominal. Si la promesse est rejetée, l'erreur remonte au error boundary le plus proche (module suivant). La promesse doit être stable : créer un nouveau fetch à chaque rendu relancerait la requête sans fin. En pratique, c'est une bibliothèque (React Query) ou le framework qui gère ce cache pour toi.

Placer ses boundaries

Tout ce qui est dans un même <Suspense> apparaît ensemble. Des boundaries imbriquées permettent d'afficher chaque zone dès qu'elle est prête. Le bon découpage suit ce que l'utilisateur perçoit comme un bloc.

Résilience

Error boundaries : contenir les erreurs

Objectifs

  • Comprendre ce qui arrive sans error boundary, et ce qu'elle change.
  • Utiliser la bibliothèque react-error-boundary et savoir lire la version classe.
  • Savoir quelles erreurs sont capturées, et lesquelles ne le sont pas.
  • Combiner error boundary et Suspense.

Le problème

Par défaut, si un composant lève une erreur pendant son rendu, React retire toute l'interface de l'écran. Une faute de frappe dans un petit widget, et l'utilisateur se retrouve devant une page blanche.

Une error boundary est un composant qui capture les erreurs de son sous-arbre et affiche un contenu de secours à la place de la partie cassée. Le reste de la page continue de fonctionner.

Analogie

C'est le tableau électrique d'un appartement, avec un disjoncteur par pièce. Un court-circuit dans la cuisine coupe la cuisine, pas tout l'appartement. Tu décides où poser les disjoncteurs.

Côté backend

C'est un try/catch autour d'un sous-arbre, ou le middleware de gestion d'exceptions d'ASP.NET et les exception handlers de FastAPI. À la différence près qu'on peut en placer plusieurs, à différents niveaux de l'interface.

La version classe, à savoir lire

Il n'existe toujours pas de hook pour écrire une error boundary : la documentation de React indique qu'il faut une classe. C'est le seul cas où tu en écriras peut-être une.

En pratique : react-error-boundary

La documentation officielle suggère aussi la bibliothèque react-error-boundary, qui fournit le composant tout fait, avec un bouton « réessayer » et un hook pour les erreurs asynchrones.

Pratique

Débugger une application React

Objectifs

  • Maîtriser les outils : console, React DevTools, onglet Réseau, points d'arrêt.
  • Suivre une méthode reproductible au lieu de tâtonner.
  • Reconnaître les messages d'erreur et symptômes classiques et leur cause.

La boîte à outils

OutilCe qu'il te dit
Console du navigateur (F12)Erreurs en rouge, avertissements React en jaune. Lis la component stack : elle indique dans quel composant l'erreur s'est produite.
React DevTools, onglet ComponentsL'arbre de composants, avec pour chacun ses props, son état, ses hooks et les contextes lus. Tu peux modifier une valeur en direct, et sélectionner un élément de la page pour trouver son composant.
React DevTools, onglet ProfilerQuels composants se sont rendus pendant une interaction, combien de temps, et pourquoi (option « Record why each component rendered »).
Réglage Highlight updatesFait clignoter à l'écran les composants qui se re-rendent, comme la démo du module 07.
Onglet Réseau (Network)La requête est-elle partie ? Quel statut ? Quel corps de réponse ? Une erreur CORS ?
Points d'arrêt (onglet Sources, ou l'instruction debugger;)Mettre le code en pause et inspecter les variables. Vite fournit les source maps : tu débugges ton code d'origine, pas le code compilé.

Un console.log placé dans le corps d'un composant s'affiche à chaque rendu ; placé dans un effet, il s'affiche après l'affichage ; placé dans un gestionnaire, il s'affiche au clic. Choisis l'endroit selon ce que tu veux observer.

Côté backend

Beaucoup de « bugs React » sont des écarts de contrat avec l'API. ASP.NET sérialise en camelCase par défaut (firstName), alors qu'une API Python renvoie souvent du snake_case (first_name). Le composant lit user.firstName, reçoit undefined, et n'affiche rien, sans aucune erreur. Le premier réflexe : ouvrir l'onglet Réseau et lire la vraie réponse.

Une méthode en cinq étapes

  1. Reproduiretrouver les étapes exactes qui déclenchent le bug.
  2. Localiserquel composant affiche la mauvaise chose ? (sélecteur des DevTools)
  3. Inspecterses props et son état sont-ils corrects ?
  4. Corrigerune hypothèse, une modification minimale.
  5. Vérifierle bug a disparu, rien d'autre n'a cassé, la console est propre.

L'étape 3 est le cœur du diagnostic, grâce au flux unidirectionnel :

  • Les props sont fausses : le problème est plus haut. Remonte au parent qui les fournit.
  • L'état est faux : cherche les appels à son setter. Qui l'appelle, avec quelle valeur ?
  • Props et état sont justes, mais l'affichage est faux : le bug est dans le JSX ou dans un calcul de ce composant.
  • Les données de l'API sont fausses : le problème est côté backend, ou dans la façon de les appeler.
