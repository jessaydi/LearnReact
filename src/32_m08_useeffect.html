08

Hooks · l'extérieur

useEffect : se synchroniser avec l'extérieur

Objectifs

  • Comprendre à quoi sert un effet, et ce qui le distingue d'un gestionnaire d'événement.
  • Savoir quand un effet s'exécute, selon son tableau de dépendances.
  • Écrire un nettoyage pour chaque ressource ouverte, et comprendre pourquoi StrictMode lance l'effet deux fois.
  • Charger des données sans afficher une réponse périmée.
  • Reconnaître les effets inutiles, de loin l'erreur la plus fréquente.

Le problème : faire quelque chose parce qu'on est affiché

Jusqu'ici, notre code se rangeait dans deux cases :

  • le rendu : calculer le JSX à partir des props et de l'état. Il doit rester pur (module 07) ;
  • les gestionnaires d'événements : réagir à une action précise de l'utilisateur (un clic, un envoi).

Certains besoins ne rentrent dans aucune des deux. Le salon de discussion doit se connecter au serveur dès qu'il est affiché, pas quand on clique. Le titre de l'onglet doit afficher le nombre de messages non lus tant que la page est ouverte. Un minuteur doit tourner pendant que le chronomètre est à l'écran.

Ces besoins ont un point commun : ils concernent un système extérieur à React (le réseau, le navigateur, un minuteur, un widget tiers) qu'il faut garder d'accord avec ce qui est affiché. C'est le rôle d'un effet.

Analogie

Une chambre d'hôtel. Quand tu entres, tu allumes la lumière. Quand tu pars, tu l'éteins. Si tu changes de chambre, tu éteins l'ancienne avant d'allumer la nouvelle. Un effet suit exactement ces trois temps : une mise en place, un nettoyage, et on recommence quand la « chambre » (une dépendance) change.

Anatomie d'un effet

Lis cet effet comme une phrase : « tant que ce composant est affiché avec ce roomId, il doit y avoir une connexion à ce salon ». Tu décris l'état dans lequel doit être l'extérieur, et React s'occupe de connecter et déconnecter au bon moment.

Quand l'effet s'exécute-t-il ?

Un effet ne s'exécute jamais pendant le rendu. Il passe en dernier, une fois l'écran à jour :

  1. RenduReact appelle ChatRoom, qui renvoie son JSX. useEffect ne fait qu'enregistrer la fonction pour plus tard.
  2. CommitReact met le DOM à jour : le titre « Salon général » existe.
  3. Peinturele navigateur affiche l'écran. L'utilisateur voit déjà le salon.
  4. EffetReact exécute ta fonction : la connexion s'ouvre.

Sur toute la vie du composant, voici ce que fait React avec l'effet du salon :

Montage
roomId = « général »

rendueffet : connexion à « général »

Re-rendu
autre état modifié, roomId identique

rendueffet ignoré : dépendances identiques

Re-rendu
roomId devient « aide »

rendunettoyage : déconnexion de « général »effet : connexion à « aide »

Démontage
le salon disparaît de l'écran

nettoyage : déconnexion de « aide »

Remarque que le nettoyage utilise toujours les valeurs de son rendu (la photo du module 07) : il déconnecte « général », pas « aide ».

Le tableau de dépendances

Le second argument de useEffect dit à React quand refaire l'effet. Il y a trois formes :

ÉcritureL'effet s'exécute…Usage
useEffect(fn)après chaque rendurare ; souvent un oubli
useEffect(fn, [])après le premier rendu seulement (le montage)abonnement global, initialisation unique
useEffect(fn, [a, b])après le premier rendu, puis chaque fois que a ou b a changéle cas normal

Après chaque rendu, React compare chaque dépendance à sa valeur du rendu précédent, avec Object.is, comme pour l'état. Si toutes sont identiques, l'effet est ignoré. Choisis un mode, puis provoque des rendus et regarde le journal :

Démo · quand l'effet s'exécute-t-il ?

userId = 1 · connecté à : utilisateur 1

  • Pas de tableau : déconnexion et reconnexion à chaque rendu, même quand rien d'utile n'a changé.
  • [] : l'effet ne tourne qu'au montage. Change userId : on reste connecté à l'ancien utilisateur. C'est un bug.
  • [userId] : l'effet ne se relance que lorsque userId change. C'est la bonne version.

À retenir · la règle des dépendances

Toute valeur du composant utilisée dans l'effet (props, état, fonctions déclarées dans le composant) doit figurer dans le tableau. Tu ne choisis pas les dépendances : elles découlent du code de l'effet. La règle ESLint react-hooks/exhaustive-deps les vérifie pour toi.

Le nettoyage

Toute ressource ouverte dans un effet doit être refermée dans son nettoyage : connexion, abonnement, minuteur, écouteur d'événement. Sinon, les ressources s'accumulent à chaque changement : deux connexions ouvertes, deux minuteurs qui tournent, des écouteurs en double.

Côté backend

La fonction de nettoyage joue le rôle d'un bloc with (__exit__) ou d'un finally en Python, ou d'un using / Dispose() en C# : ce qui est ouvert doit être fermé, quoi qu'il arrive.

StrictMode : pourquoi ton effet s'exécute deux fois

Coche « StrictMode » dans la démo ci-dessus et réinitialise. Au montage, tu vois : effet, nettoyage, effet. En développement, React monte le composant, le démonte aussitôt, puis le remonte. C'est un test automatique : si ton effet a un nettoyage correct, l'utilisateur ne voit aucune différence (on se retrouve avec une seule connexion). S'il en manque un, le bug apparaît tout de suite, en développement, plutôt que des semaines plus tard en production.

Piège

Ne désactive pas StrictMode pour « corriger » un effet lancé deux fois. Le double appel n'est pas le problème : il révèle un nettoyage manquant. En production, l'effet ne s'exécute qu'une fois au montage.

Les pièges classiques

1. La boucle infinie

Un effet qui modifie l'état provoque un rendu. Si ce rendu relance l'effet, on tourne en rond :

Le symptôme : l'erreur Maximum update depth exceeded, ou une requête qui part en boucle dans l'onglet Réseau.

2. La closure périmée

Au module 07, on a vu qu'une fonction garde les valeurs de son rendu. Avec un minuteur lancé une seule fois, c'est un piège :

Démo · la closure périmée

setSeconds(seconds + 1)

0

lit la valeur figée du premier rendu

setSeconds(s => s + 1)

0

demande à React la valeur la plus récente

À gauche, chaque seconde calcule 0 + 1 : le compteur reste bloqué à 1. À droite, la forme fonction reçoit toujours la valeur à jour. Quand un minuteur ou un abonnement met à jour l'état, utilise la forme fonction du setter.

3. L'effet qui ne devrait pas exister

C'est l'erreur la plus répandue, y compris dans le code généré par une IA : utiliser un effet pour quelque chose qui n'a rien d'extérieur.

4. L'effet async

useEffect(async () => …) ne fonctionne pas : une fonction async renvoie une promesse, alors que React attend soit rien, soit une fonction de nettoyage. Déclare une fonction async à l'intérieur de l'effet et appelle-la, comme load() dans UserProfile.

As-tu vraiment besoin d'un effet ?

Réponds aux questions pour un besoin précis que tu as en tête :

Aide à la décision

    Ce code doit-il s'exécuter parce que l'utilisateur a fait une action précise (un clic, un envoi, une frappe) ?

    Veux-tu calculer une valeur à partir des props ou de l'état (un total, une liste filtrée, un nom complet) ?

    Veux-tu remettre un état à zéro quand une prop change (changer d'utilisateur, de fiche) ?

    Dois-tu te connecter à quelque chose que React ne gère pas (API du navigateur, WebSocket, minuteur, widget tiers, titre de l'onglet) ?

    Dois-tu charger des données depuis ton API ?

    Pas d'effet : un gestionnaire d'événement

    Mets le code dans onClick ou onSubmit. L'action est causée par l'utilisateur, pas par l'affichage.

    Pas d'effet : un calcul pendant le rendu

    Écris const total = items.reduce(…) directement dans le composant. Pas d'état en plus, pas d'effet.

    Pas d'effet : une key

    Écris <Form key={userId} />. Quand la key change, React recrée le composant avec un état neuf (module 07).

    Oui, c'est un effet

    Écris la mise en place, le nettoyage qui la défait, et laisse le linter compléter les dépendances.

    Un effet, ou mieux, une bibliothèque

    Un effet avec le drapeau ignore fonctionne. Dans un vrai projet, préfère React Query ou le chargement de données du framework.

    Probablement pas d'effet

    Formule le besoin à voix haute : s'il ne parle ni d'un système extérieur ni de données à charger, il relève du rendu ou d'un gestionnaire.

    Deux noms à connaître sans t'y attarder : useLayoutEffect s'exécute avant que le navigateur peigne l'écran (rare, pour mesurer un élément) ; useEffectEvent, stable depuis React 19.2, permet de lire la dernière valeur d'une prop dans un effet sans la mettre dans les dépendances.

    En bref

    • Un effet synchronise le composant avec un système extérieur. Il s'exécute après l'affichage, jamais pendant le rendu.
    • Les dépendances découlent du code de l'effet : toute valeur du composant qu'il utilise doit y figurer.
    • Tout ce qui est ouvert est refermé dans le nettoyage. StrictMode le vérifie en lançant l'effet deux fois en développement.
    • Pour charger des données, protège-toi des réponses périmées avec un drapeau ignore.
    • Un calcul ou une réaction à un clic ne sont jamais des effets.

    Lequel de ces besoins justifie vraiment un useEffect ?

    Le total se calcule pendant le rendu, l'envoi se fait dans le gestionnaire de clic. Seul l'abonnement WebSocket synchronise le composant avec un système extérieur, avec un nettoyage pour se désabonner.

    On clique sur l'utilisateur 1 puis aussitôt sur l'utilisateur 2. La réponse du 1 arrive en dernier. Que fait le drapeau ignore ?

    Quand userId passe de 1 à 2, React appelle le nettoyage du premier effet, qui lève son drapeau. La requête du 1 se termine quand même, mais son résultat est ignoré. Pour vraiment l'annuler, on utiliserait un AbortController.
