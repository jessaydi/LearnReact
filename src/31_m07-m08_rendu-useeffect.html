07

Modèle mental

Le cycle de rendu : ce qui se passe vraiment

Objectifs

  • Savoir ce qui déclenche un rendu et ce qui se passe ensuite.
  • Comprendre pourquoi un rendu doit rester pur, et ce que fait StrictMode.
  • Décider où placer un état partagé (« remonter l'état »).

Ce module est le plus important pour débugger. La plupart des bugs React viennent d'une idée fausse sur le moment où le code s'exécute.

Les quatre temps

  1. Déclenchementpremier affichage, ou un setter appelé quelque part.
  2. RenduReact appelle tes composants pour obtenir le nouveau JSX. Rien ne change encore à l'écran.
  3. CommitReact compare avec le JSX précédent et applique au DOM les différences minimales.
  4. Effetsune fois l'écran à jour, React exécute les useEffect concernés (module 08).

Le rendu est un calcul, le commit est une écriture. Comme dans Terraform : plan, puis apply.

Qu'est-ce qui déclenche un nouveau rendu ?

  1. Son propre état change : un setter est appelé avec une nouvelle valeur.
  2. Son parent se re-rend : par défaut, tous les enfants se re-rendent aussi, même si leurs props n'ont pas changé.
  3. Un contexte qu'il lit change (module 10).

Les props ne sont pas une cause à part : si les props d'un composant changent, c'est que son parent s'est re-rendu.

Démo · qui se re-rend ?
  • App état : theme 1
    • Header 1
    • TaskList état : filter 1
      • TaskItem n°1 1
      • TaskItem n°2 état : isEditing 1
      • TaskItem n°3 1
    • Footer 1

Clique sur un bouton. Les composants qui se re-rendent clignotent et leur compteur de rendus augmente.

Re-rendre n'est pas repeindre

Un re-rendu, c'est l'appel de fonctions JavaScript. C'est généralement très rapide. Le DOM, lui, n'est modifié que là où le résultat diffère. N'essaie pas d'éviter les re-rendus « par principe » : optimise seulement quand tu mesures un vrai problème (module 09).

Un rendu doit être pur

Mêmes props, même état, même contexte : même JSX. Et aucun effet de bord pendant le calcul.

Les effets de bord ont deux places légitimes : les gestionnaires d'événements (en réponse à une action) et useEffect (pour se synchroniser avec l'extérieur).

À retenir

En développement, StrictMode appelle volontairement tes composants deux fois, et monte-démonte-remonte tes effets, pour révéler les impuretés. Si tes console.log apparaissent en double, ce n'est pas un bug. En production, chaque rendu n'a lieu qu'une fois.

Où vit l'état ? Remonter l'état

Deux composants frères ont besoin de la même donnée : une barre de recherche écrit la requête, une liste la lit. Si l'état est dans SearchBar, TaskList ne peut pas le voir. Solution : le déplacer chez leur parent commun le plus proche.

Règle : place l'état le plus bas possible, mais assez haut pour que tous ceux qui en ont besoin soient en dessous. Une seule source de vérité, comme une donnée partagée entre deux services backend : on lui donne un propriétaire unique au lieu de la dupliquer.

Comment React sait quel état appartient à qui

React associe l'état à la position du composant dans l'arbre, à son type et à sa key. Pas au nom de ta variable.

Dernier point du modèle mental : chaque rendu a ses propres props, son propre état et ses propres fonctions. Une fonction créée pendant le rendu n°3 « voit » les valeurs du rendu n°3, pour toujours. Retiens-le, on s'en servira au module 08.

Un parent se re-rend. Les props de son enfant sont identiques. L'enfant se re-rend-il ?

Par défaut, un re-rendu descend tout le sous-arbre. On peut l'éviter avec memo ou le React Compiler (module 09), mais ce n'est utile qu'en cas de lenteur mesurée : le DOM n'est de toute façon modifié que là où le résultat change.

Filters et ResultsTable sont frères et ont besoin du même filtre. Où vit l'état ?

Un frère ne peut pas passer de props à un autre frère. On remonte l'état chez le parent commun, qui donne la valeur aux deux et un callback à celui qui la modifie. Deux états synchronisés par un effet, c'est deux sources de vérité.

08

Hooks · l'extérieur

useEffect : se synchroniser avec l'extérieur

Objectifs

  • Savoir quand un effet s'exécute, selon son tableau de dépendances.
  • Écrire un nettoyage pour chaque ressource ouverte.
  • Charger des données proprement, sans réponse périmée.
  • Reconnaître les effets inutiles, de loin l'erreur la plus fréquente.

À quoi sert un effet

Un effet sert à synchroniser ton composant avec un système qui n'est pas géré par React : le réseau, un timer, une API du navigateur, une connexion WebSocket, un widget tiers, le titre de l'onglet.

Il s'exécute après que l'écran a été mis à jour. Le rendu reste donc pur, et l'effet fait le travail « sale » ensuite.

Le tableau de dépendances

ÉcritureL'effet s'exécute…Usage
useEffect(fn)après chaque rendurare ; souvent un oubli
useEffect(fn, [])après le premier rendu seulement (le montage)abonnement global, initialisation unique
useEffect(fn, [a, b])après le premier rendu, puis quand a ou b a changéle cas normal

« A changé » se vérifie par référence (Object.is), comme pour l'état. Choisis un mode, puis provoque des rendus et regarde le journal :

Démo · quand l'effet s'exécute-t-il ?

Le nettoyage

Côté backend

La fonction de nettoyage, c'est ton Dispose(), ton bloc using, ton __exit__ ou ton finally. Toute ressource ouverte dans un effet (connexion, abonnement, timer, écouteur d'événement) doit être refermée dans son nettoyage. Sinon : fuites mémoire, doublons, comportements fantômes.

À retenir

En développement, StrictMode monte le composant, le démonte, puis le remonte : ton effet s'exécute deux fois, avec un nettoyage entre les deux. Si un effet casse quand il est lancé deux fois, il lui manque un nettoyage. Ne désactive pas StrictMode pour « corriger ».

Charger des données

Pourquoi le drapeau ignore ? Tu cliques sur l'utilisateur 1 puis, vite, sur le 2. Les réponses peuvent arriver dans le désordre. Si celle du 1 arrive en dernier, sans le drapeau, tu afficherais le mauvais profil. Le nettoyage marque l'ancienne requête comme périmée.

À retenir

C'est verbeux, et il manque encore le cache, les nouvelles tentatives et le rafraîchissement. C'est exactement ce que React Query fera pour toi, ton prochain sujet. Comprendre ce code te permettra de comprendre ce que la bibliothèque automatise.

Les pièges classiques

1. La boucle infinie

2. Les dépendances manquantes

Toute valeur du composant utilisée dans l'effet (props, état, fonctions déclarées dans le composant) doit figurer dans le tableau. Sinon l'effet travaille avec des valeurs d'un ancien rendu. La règle ESLint react-hooks/exhaustive-deps te le signale : écoute-la, et ne la fais jamais taire avec un commentaire eslint-disable.

3. La closure périmée

4. L'effet qui ne devrait pas exister

5. L'effet async

useEffect(async () => …) ne fonctionne pas : une fonction async renvoie une promesse, alors que React attend une fonction de nettoyage. Déclare une fonction async à l'intérieur de l'effet et appelle-la, comme dans UserProfile.

À retenir · as-tu besoin d'un effet ?

  • Calculer une valeur à partir des props ou de l'état : non, calcule-la pendant le rendu.
  • Réagir à un clic ou à une soumission : non, mets le code dans le gestionnaire.
  • Remettre un état à zéro quand une prop change : souvent non, utilise une key.
  • Se connecter à un système extérieur (API du navigateur, socket, timer, widget tiers) : oui.
  • Charger des données : oui en React seul ; en pratique, une bibliothèque comme React Query ou le framework s'en charge.

Deux noms à connaître sans t'y attarder : useLayoutEffect s'exécute avant que le navigateur peigne l'écran (rare, pour mesurer un élément) ; useEffectEvent, stable depuis React 19.2, permet de lire la dernière valeur d'une prop dans un effet sans la mettre dans les dépendances.
